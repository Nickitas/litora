# AGENTS.md

Инструкции для AI-агентов и разработчиков монорепозитория Litora.

## Перед началом работы

1. Проверить `git branch --show-current`, `git status` и локальные инструкции.
   Рабочая `development` должна происходить от монорепозиторного `main`, а не
   от старой source-ветки web. Не перезаписывать существующие изменения пользователя.
2. Прочитать [SDD](sdd/README.md) и связанные с задачей спецификации:
   [технические](sdd/tesh-specs.md),
   [бизнес-логику](sdd/buisnec-logic.md),
   [дизайн](sdd/design-system.md),
   [deployment](sdd/deployment.md).
   Для локального запуска — [инструкция](sdd/development.md).
3. Сопоставить описание с кодом. Различать реализованное, конвенцию и план;
   не заявлять, что описанный функционал уже работает.
4. Для новой функции определить границы, риски и проверяемые требования по
   [шаблону](sdd/templates/feature.md). Диагностика сама по
   себе не разрешает исправления; непонятный пересекающийся diff требует уточнения.
5. Новая технология, изменение прав, платный сервис и внешняя интеграция требуют
   обоснования и согласования, а не неявного расширения задачи.

## Язык

Пользовательский интерфейс, сообщения CLI/API, документация и комментарии к
экспортируемому коду пишутся на русском языке. Имена программных сущностей,
HTTP-полей и технические идентификаторы остаются на английском.

## Назначение системы

Litora — платформа для расчётов и исследований береговой линии и рельефа дна
Чёрного моря. Go является единственным источником математической и научной
логики. TypeScript-приложения не должны дублировать формулы или алгоритмы.

## Компоненты и ответственность

### `apps/lito-cli`

- самостоятельное CLI-приложение и вычислительное ядро;
- чтение и валидация геоданных, расчёты, построение сеток и отчётов;
- генерация машинно-читаемого манифеста результата;
- не отвечает за пользователей, авторизацию, HTTP и долговременное хранение.

Доменная логика находится в Go-пакетах и не зависит от Cobra. Cobra — только
транспортный адаптер. Новые расчёты должны вызываться и из CLI, и из Go worker.

### `apps/lito-api`

- NestJS control plane и единственный публичный backend для web;
- регистрация, авторизация, пользователи и права доступа;
- приём параметров, создание заданий и выдача результатов;
- метаданные в PostgreSQL, файлы через S3 API;
- не содержит научных формул и не выполняет расчёты внутри HTTP-запроса.

### `apps/lito-web`

- React-интерфейс, работающий через `@litora/api-client`;
- не обращается напрямую к PostgreSQL, S3 или процессу CLI;
- не дублирует DTO и серверную бизнес-логику.

### Общие пакеты

- `packages/contracts` — публичные DTO, статусы заданий и типы API;
- `packages/api-client` — типизированный HTTP-клиент;
- `packages/config` — общая безопасная конфигурация без секретов;
- `packages/docs/content` — единственный источник общей документации;
- `packages/generated-data` — небольшие версионируемые примеры и артефакты.

## Целевой поток расчёта

1. Web отправляет параметры через API client.
2. API проверяет пользователя и DTO, создаёт `calculation_job` в PostgreSQL.
3. Go worker получает задание и запускает вычислительное ядро.
4. Worker загружает крупные артефакты в S3-совместимое хранилище.
5. Worker записывает статус, метрики и ссылки на артефакты в PostgreSQL.
6. API возвращает web состояние и временные подписанные URL файлов.

На первом этапе допустим запуск CLI как дочернего процесса из отдельного worker.
Запуск CLI непосредственно из controller запрещён.

Текущий worker находится в `apps/lito-api/src/worker/main.ts` и запускается отдельным
процессом. Очередь — PostgreSQL `FOR UPDATE SKIP LOCKED`; SQL-запросы пользовательского
API обязательно фильтруются по `user_id`. Новые сценарии включаются через разрешённый
набор в `calculations/commands.ts`, без произвольных аргументов shell, путей и URL.
Для CLI доступен `--manifest <output>/manifest.json`. План интеграции и ограничения:
`packages/docs/content/platform-integration.md`.

## Инфраструктурные решения

- PostgreSQL обязателен для пользователей, сессий, заданий, статусов, метаданных
  результатов и аудита.
- S3-совместимое хранилище обязательно для входных файлов и крупных результатов.
  Локально используется MinIO, в production — AWS S3 или совместимый сервис.
- Docker Compose используется для локальных PostgreSQL и MinIO.
- Redis не добавляется до подтверждённой потребности. Сначала очередь строится на
  PostgreSQL с безопасным захватом заданий worker'ом.
- Крупные расчётные файлы не хранятся в PostgreSQL и не коммитятся в Git.

## Контракты и совместимость

Изменение API выполняется в порядке:

1. `packages/contracts`;
2. controller/service в `apps/lito-api`;
3. `packages/api-client`;
4. потребитель в `apps/lito-web`;
5. Swagger и документация.

Статусы задания: `queued`, `running`, `succeeded`, `failed`, `cancelled`.
Каждый расчёт имеет UUID, владельца, тип, версию ядра, входные параметры,
временные метки и список артефактов.

## Безопасность

- секреты берутся только из environment variables и не коммитятся;
- пароли хешируются Argon2id, пароль никогда не возвращается через API;
- access token короткоживущий, refresh sessions отзывные и хранятся в PostgreSQL;
- S3-объекты приватные, доступ выдаётся через ограниченные signed URL;
- входные файлы проверяются по размеру, типу и контрольной сумме;
- запросы на данные ограничиваются владельцем или ролью пользователя.

Сейчас jobs ограничены именно владельцем; `role=admin` в БД не означает готовый
административный API. Расширение прав требует контракта и отрицательных тестов.
Access/refresh — opaque tokens, не JWT; access только в памяти web, refresh в
HttpOnly cookie. Не логировать секреты, токены и signed URL.

## Как писать и менять код

- Сначала contracts и runtime-валидация, затем реализация и потребители.
  TypeScript-тип не заменяет проверку внешнего ввода.
- TS: strict, `unknown` на внешней границе, параметризованный SQL, явные ошибки;
  не ослаблять конфигурацию и не добавлять `any`/`@ts-ignore` ради зелёной сборки.
- Go: `gofmt`, ошибки с контекстом, Context для долгих операций; чистые доменные
  функции отдельно от Cobra, тесты численной точности и граничных входов.
- При изменении реализации одного из опубликованных Go-методов повышать его
  ревизию в `internal/domain/methods`, проверять манифест CLI и сквозной путь
  worker → API → web. Ревизия реализации не означает научную аттестацию.
- Не заменять отсутствующие научные данные выдуманными. Фиксировать CRS, единицы,
  nodata, источник, версию и ограничения применимости модели.
- React: функциональные компоненты, существующие слои, запросы через api-client,
  cleanup polling/effects; не копировать DTO или бизнес-логику API.
- UI: сохранять shadcn `radix-nova`, Radix, Tailwind 4, Lucide. Новые элементы
  следуют semantic tokens темы «Чёрное море». Тема ещё не полностью внедрена;
  не смешивать миграцию всех экранов с несвязанной задачей.
- Loading, empty, ошибка, отмена и отсутствие доступа — отдельные состояния.
  Клавиатура, label/focus, мобильный экран и обе темы входят в приёмку UI.
- SQL — новые нумерованные миграции; опубликованные миграции и schema_migrations
  не редактировать. Заранее определить совместимость и восстановление.
- Предпочитать ясную малую реализацию. Рефакторинг и новая зависимость служат
  текущей задаче, а не предполагаемой будущей архитектуре.

## Документация

Изменение поведения требует обновления документов для соответствующей аудитории.
Инженерные спецификации и правила разработки живут только в `sdd/`. Научные
методики, описания возможностей и справочник для читателя сайта — только в
`packages/docs/content/`. Не помещать SDD в пакет сайта и не дублировать его
там. `AGENTS.md` — обязательный операционный вход для агента, с ссылками на SDD.
Web импортирует Markdown из `packages/docs/content/**/*.md`, поэтому любой SDD-файл
внутри этого пакета попадёт в сборку сайта.
`apps/lito-cli/docs` и symlink не восстанавливать. Новые экспортируемые Go-типы
и функции документируются godoc-комментариями. Добавление markdown в SDD не
создаёт страницу в меню сайта.

Обновлять требования/приёмку, Swagger, инструкции и статус реализации вместе
с поведением. Архитектурный выбор фиксировать в ADR с альтернативами и последствиями.

## Правила CLI

Результаты команд сохраняются в `apps/lito-cli/output/` или в явно переданный
`--output`. Табличный вывод формируется через `text/tabwriter`, разделитель — `\t`,
заголовки — на русском языке.

## Проверки

Единый gate для изменений в приложении — `pnpm verify`; интеграционный тест требует
отдельного локального или тестового окружения.

```bash
pnpm typecheck
pnpm --filter litora-api build
pnpm --filter litora-web build
pnpm test:api
cd apps/lito-cli && go test ./...
```

Запускайте проверки пропорционально затронутым компонентам.

- Docs-only: ссылки, согласованность с кодом, `git diff --check`.
  Compose/Caddy-примеры валидировать, не разворачивать без поручения.
- Web: дополнительно `pnpm --filter litora-web lint` и проверка изменённого UI.
- Go: `go vet ./...`; при затронутой конкурентности также `go test -race ./...`.
- Auth/jobs/S3/миграции: `pnpm test:integration` только на тестовом окружении.
  Скрипт создаёт реальные записи и файлы; не запускать на production без отдельного
  согласования. Typecheck не является проверкой интеграции.
- Указать команды, результат, пропущенные проверки и причины. Не скрывать сбои
  и не объявлять production-ready по одному `health=200`.

## Что нельзя делать без отдельного поручения

- Коммитить, push/force-push, публиковать релиз, удалять старые репозитории или
  переписывать историю/LFS. В текущем процессе коммит делает пользователь.
- `reset --hard`, очистка чужого diff, рекурсивное удаление широких каталогов.
- `docker compose down -v`, volume prune, удаление БД/bucket и массовый cleanup;
  сначала точные цели, backup и согласование потери данных.
- Загружать секреты в Git, tool output, публичные issue или клиентский bundle.
- Выполнять CLI в controller, принимать shell/путь/URL команды из запроса,
  обходить owner-проверку или делать bucket публичным ради устранения 403.
- Вводить Redis, ORM, второй UI-kit, Kubernetes или научные формулы в TS без
  согласованного архитектурного решения.
- Публиковать локальный Compose с default-паролями/MinIO `latest` как production;
  использовать отдельный runbook и проверенный поддерживаемый S3.

Перед завершением проверить diff и отсутствие секретов/крупных артефактов.
Кратко перечислить изменения, результаты проверок, риски и оставшиеся шаги.
Не утверждать, что система развёрнута, если созданы лишь инструкции и шаблоны.
