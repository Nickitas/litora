# План развития Litora

Сверено с кодом 18.10.2026: development, исходный SHA 756610b и текущие
локальные изменения. [x] — выполнен названный результат с указанной проверкой;
[~] — частичная реализация или незаконченная приёмка; [ ] — следующий шаг.
Реализация, научная проверка и выпуск — разные результаты. Локальный тест не
подтверждает staging, а незакоммиченный код не является выпущенной версией.

## Цель и границы

Litora даёт два пути к одной научной логике Go: самостоятельный CLI без аккаунта
и лабораторию /lab через API, очередь и приватное хранилище. Пользователь
сохраняет входы с паспортом, запускает расчёт, изучает результат и продолжает
исследование на его основе. Лаборатория должна быть воспроизводимой, понятной и
устойчивой к сбоям; отдельный /account пока содержит только профиль.

Покрытие CLI означает проверенные научные сценарии с типизированными входами,
а не удалённое выполнение произвольной команды. Полный перенос всех флагов
не является условием ближайшего пилота: серверные значения и ограничения
фиксируются в [матрице флагов](../sdd/cli-web-flag-matrix.md).
Go остаётся единственным источником формул и научной валидации.

Требования и эксплуатация живут в sdd/; научные методики и пользовательский
справочник — в packages/docs/content/. Детальный UI-план ведётся в
[account-roadmap.md](account-roadmap.md), научный прогноз — в
[срезе 0048](../sdd/features/0048-annual-shoreline-forecast.md). Здесь — общие
приоритеты, зависимости и критерии готовности без дублирования всех подзадач.

  считать выпущенными или повторно планировать как отсутствующую реализацию.

  Основание выпуска — протокол для конкретного SHA, окружения и входных SHA-256.

  общая квота входов вместе с результатами, приёмочная матрица сценариев и
  научные данные пилота.

## Матрица CLI → API → лаборатория

Сверять с [реестром команд](../sdd/cli-capabilities.md),
calculations/commands.ts и [0027](../sdd/features/0027-web-cli-scientific-workflows.md).
В коде зарегистрирован 21 HTTP-kind; heavy-сценарии выдаются каталогом только при
LITO_HEAVY_ENABLED=true. Это разрешение конфигурации, а не проверка живого worker.
«Локально» ниже означает наличие пути в коде; приёмка одинаковых научных входов
CLI и worker остаётся отдельной задачей.

| Сценарий CLI | Реализация API/web | Оставшийся результат |
| --- | --- | --- |

## A. Данные, очередь и сохранность

- [~] **A1. Сквозная приёмка.** Стандартный вертикальный срез и негативные
  сценарии уже проверялись локально; есть scripts/integration-test.mjs, DB-
  тесты и браузерные сценарии. Нужен повторяемый протокол для текущего SHA:
  окружение, версии Go/Gmsh, входные hashes, исполненные/пропущенные сценарии,
  время и итог. Отдельно включить удаление с зависимостями, восстановление
  сессии и загрузку модулей после нового web-релиза. Реальные тесты создают
  данные только в выделенном тестовом окружении.
- [~] **A2. Реестр возможностей.** Команды и флаги автоматически сверяются
  pnpm check:workspace; покрытие по параметрам есть в матрице флагов.
  Остались лицензии/версии реальных входов и измеренные профили. Не писать
  второй подробный реестр в этом плане.
- [~] **A3. Воспроизводимость.** Есть версии схем, coreVersion, SHA-256,
  приватные копии встроенных входов и provenance. Нужны стабильные ревизии
  остальных опубликованных Go-методов, проверенные датумы/единицы/nodata,
  версии Gmsh и исходных наборов, численные допуски сравнения. Повтор формы
  сейчас использует актуальное ядро, а не воспроизводит исторический binary.
- [~] **A4. Научные загрузки.** Приватные роли файлов, потоковый upload,
  checksum, pending/uploading/ready, owner-lock при резервировании и лимиты
  20 файлов/2 ГиБ на владельца уже есть. Владелец может удалить pending;
  uploading разрешено перехватить через четыре часа. Следующее: приёмка
  конкурирующих загрузок, видимый расход квоты, согласованные сроки резерваций
  и уборка брошенных объектов после сбоев. Научная проверка совместимости
  остаётся в Go; API-ready не означает научно пригоден.
- [~] **A5. Ресурсы и очередь.** Есть standard/heavy, атомарный claim,
  heartbeat job, timeout, отмена, output-budget и отдельные контейнерные лимиты.
  Первый шаг наблюдения — 0050, проверен локально. Далее: heartbeat idle worker и capabilities
  профиля; проверка отсутствующего heavy worker; измеренные CPU/RAM/temp;
  жёсткая квота временного диска и crash/restart/cancel тесты. Новый брокер
  очереди не требуется без измеренной потребности.
- [~] **A6. Жизненный цикл.** Есть частичная уборка failed/cancelled,
  read-only reconciliation и отдельная очередь удаления собственных завершённых
  jobs с защитой зависимостей ([0043](../sdd/features/0043-account-calculation-deletion.md)).
  Локальная очистка пяти старых дублей dataset не является общим API удаления.
  Нужны согласованные retention и общая квота входов вместе с результатами,
  удаление datasets/готовых scientific inputs, версии S3 и backup,
  масштабируемая сверка и журнал действий.
  Автоматический сборщик включать после проверенного dry-run и восстановления.

## Отложено и не требуется для ближайшего пилота

- Переписывание worker на Go, Redis, Kubernetes и распределённая очередь без
  измеренного узкого места.
- Автоматический сетевой source-url в web: локальная загрузка закрывает
  текущую потребность; внешний импорт потребует SSRF-защиты и лицензирования.
- Превращение каждого CLI-флага в поле формы; обоснованные серверные ограничения
  остаются в матрице. Непокрытые научные возможности не объявляются реализованными.
- Организации, общий доступ, роли экспертов, оплата и обучаемая ML-модель без
  отдельного продуктового решения. Существующий AI-02 остаётся исследованием.
- Повторное написание уже работающих истории, модалок, калибровки и upload.
  Их открытые проверки сохраняются, а дальнейший UI-backlog ведётся отдельно.

## Критерий готовности ближайшего выпуска

Для выбранного набора сценариев закреплены SHA релиза, права на данные, версии
и hashes входов, ресурсные пределы и протокол CLI ↔ worker ↔ API ↔ web.
Проверены ошибка, отмена, timeout, чужой UUID, зависимый источник и восстановление
после сбоя. Подтверждены CI, закрытый staging, TLS, backup/restore и реакция
оператора на отказ worker. Пользователь видит ограничения доступных сценариев;
непроверенные heavy-возможности не открываются более широкой аудитории.
Открытая регистрация и научный прогноз проходят свои дополнительные ворота.
