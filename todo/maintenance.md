# План завершения монорепозитория Litora

Статус сверки: 30.09.2026. Это план, а не заявление о готовности продукта или
обещание сроков. `[x]` — реализовано и имеется указанная проверка; `[~]` —
реализована лишь часть или проверка не завершена; `[ ]` — не реализовано.
Написанный код без полного сквозного прогона не считается завершённым. При работе
над очередным срезом сверять отметки с кодом, CI и staging. Незакоммиченные
изменения нельзя считать выпущенной версией.

## Цель и границы

Один репозиторий содержит самостоятельное `apps/lito-cli` и веб-платформу
`apps/lito-api` + `apps/lito-web`. Пользователь **без аккаунта** скачивает CLI,
делает научные расчёты локально и хранит файлы у себя. Пользователь **с
аккаунтом** загружает допустимые входы, запускает те же научные возможности в
кабинете, видит историю и скачивает результаты. Go — единственный источник
научной логики; API отвечает за доступ, очередь и хранение, web работает через
`@litora/api-client`.

«Полная функциональность CLI на сайте» означает покрытие его **научных**
сценариев типизированными контрактами, worker и UI, а не серверное выполнение
произвольных команд или флагов пользователя. `completion` и `--help` остаются
локальными функциями; на сайте им соответствуют установка и документация.
Если нет лицензированного входа, Gmsh или безопасного профиля ресурсов,
сценарий явно недоступен до выполнения предусловий. Локальный CLI не зависит
от API, PostgreSQL, S3 или регистрации.

Источник инженерных требований — `sdd/`; научные и пользовательские тексты
для сайта — только `packages/docs/content/`. Для каждого среза порядок:
[спецификация](../sdd/process.md) → contracts → Go/worker → API/хранение →
api-client → web/Swagger → проверки → пользовательская документация.

## 1. Матрица покрытия CLI → API → кабинет

`Частично` — только названный срез: флаги CLI и пользовательские входы не
становятся HTTP-контрактом автоматически. Полный [реестр команд](../sdd/cli-capabilities.md)
автоматически сверяется с Cobra при `pnpm check:workspace`. Для научной команды
финиш — типизированный вход, валидация, очередь, воспроизводимый manifest,
приватные файлы, UI запуска/результата и сквозной тест.

| Возможность CLI | API / web сейчас | Следующий проверяемый шаг |
| --- | --- | --- |
| `source` — источник и снимок контура | Нет | Паспорт и лицензия, безопасная проверка без произвольного URL, UI источников |
| `map black-sea` | Частично: встроенный контур | Пользовательский/версионированный контур, параметры и просмотр экспорта |
| `dimension` | Частично: встроенный контур и малый GeoJSON LineString | Масштабы, полный контур, ограничения геометрии и сопоставимые отчёты |
| `mesh` | Нет | Параметры генераторов, изолированный Gmsh, квоты и сравнение сеток |
| `seabed build` | Нет | Версионированные MSH и батиметрия, CRS/датумы, модель |
| `seabed render` | Нет | Зависимость от build, карты, изобаты, 3D и профили |
| `seabed adapt` | Нет | Зависимость от модели, поле размера и его паспорт |
| `seabed generate-adaptive` | Нет | Зависимость от поля размера, Gmsh, лимиты и отчёт качества |
| `seabed compare-adaptive` | Нет | Сравнение генераторов на общем входе, рейтинг и файлы |
| `seabed validate` | Нет | Опорная модель с паспортом, вертикальный датум и показатели ошибок |
| `seabed check-full` | Нет | Тяжёлый профиль ресурсов и отчёт полного контура |
| `seabed expert-set` | Нет | Экспертные карточки, экспорт/импорт оценок и права |
| `seabed assess-ml` | Нет | Оценки экспертов и объяснимый отчёт; не обещать обучение модели |
| `erosion` | Частично: демо CERC, только `steps` | Свои волны/берег/батиметрия, единицы и время |
| `calibrate-cerc` | Нет | Наблюдения, параметры калибровки, отчёт |
| `all` | Нет | Версионированный workflow проверки контура, размерности и CERC; сейчас не включает mesh/seabed |
| `completion`, `--help`, `--quiet` | Только CLI | Документация и скачивание; endpoints не нужны |

## 2. Этапы и задачи

`P0` — обязательный фундамент и безопасность; `P1` — функциональный
паритет; `P2` — качество использования и завершение выпуска. Каждый открытый
пункт оформлять отдельной спецификацией `sdd/features/NNNN-*.md` с
требованиями и проверками, а не одним массовым переключением. Тяжёлые сценарии
не открывать до лимитов и прав на исходные данные.

### A. Сквозная основа и входные данные (P0)

- [~] **A1. Проверить текущий вертикальный срез.** Есть четыре HTTP-kind:
  `dimension`, `dimension_dataset`, `map`, `erosion`. Первый GeoJSON-срез
  описан в [0006](../sdd/features/0006-user-coastline-datasets.md). Нужен CI/staging
  прогон HTTP → PostgreSQL → worker → Go → S3 → браузер на настоящих сервисах и
  тесты успеха, ошибки, отмены, чужого UUID, повреждённого объекта и запуска
  без загруженного файла.
  Локально 30.09.2026 изолированный Compose-проект прошёл HTTP → PostgreSQL →
  worker → Go → S3 для всех четырёх kind, включая `failed` на непригодном
  GeoJSON, `cancelled`, чужой UUID, SHA-256 и приватность bucket. Контейнеры
  и тестовые volumes удалены. Локально 30.09.2026 добавлены и пройдены
  браузерный сценарий регистрации → default GeoJSON → Go → manifest → история
  после reload и отдельный тест подменённого S3-объекта: worker отклоняет
  несовпадение SHA-256/размера до расчёта. Оба включены в интеграционный
  CI-job; его фактический результат и staging ещё не подтверждены, поэтому
  статус `[~]`.
- [~] **A2. Реестр возможностей и входов.** Все 18 зарегистрированных Cobra-команд
  описаны в [реестре](../sdd/cli-capabilities.md): входы, ключевые флаги,
  результаты, зависимости, статус прав/лицензий, ресурсный профиль и web-решение.
  `pnpm check:workspace` выявляет новую команду без записи и ошибочный флаг.
  Отдельные версии алгоритмов, подтверждённые лицензии внешних данных и
  измеренные профили тяжёлых команд ещё отсутствуют; не считать A2 завершённым.
- [~] **A3. Контракты и provenance.** Есть типы jobs и малого LineString,
  ownership, SHA-256 и `coreVersion`. Добавить версии схем входа/результата,
  CRS, горизонтальный и вертикальный датумы, единицы, nodata, время, лицензии
  и точные версии upstream datasets/jobs. Для каждого типа — негативные тесты.
- [ ] **A4. Большие входы.** Отдельные типы для волн, батиметрии, MSH и
  наблюдений; размер/число файлов, потоковая или подписанная загрузка,
  checksum, проверка формата, карантин до валидации и приватность. Не
  принимать URL, путь, shell-команду или произвольные CLI-флаги от клиента.
- [~] **A5. Ресурсы и очередь.** Уже есть один job на worker, heartbeat,
  timeout, отмена и лимит опубликованных файлов. Для mesh/seabed нужны
  профили CPU/RAM/временного диска, квоты, ограничения *во время* расчёта,
  измеренные пики и, если потребуется, отдельная тяжёлая очередь. Сохранить
  атомарные переходы и безопасный захват задания.
- [ ] **A6. Жизненный цикл данных.** Согласовать retention/квоты до крупных
  загрузок; реализовать удаление jobs/datasets/объектов, уборку orphan после
  ошибок, аудит и проверяемое восстановление.

### B. Научный паритет Go и worker (P1; после A2–A5)

- [~] **B1. Отделить ядро от Cobra.** Go-пакеты уже существуют, но worker
  запускает бинарник. Новым сценариям нужен общий программный Go API с
  типизированными параметрами; Cobra — локальный адаптер. Дочерний процесс
  из отдельного worker допустим при сохранении безопасности и паритета;
  запуск CLI из HTTP-controller запрещён.
- [ ] **B2. Добавлять сценарии малыми срезами:** `source`, расширения
  `map`/`dimension` → пользовательский `erosion` и `calibrate-cerc` →
  `mesh` → `seabed build/render/adapt` → остальные `seabed` → `all`.
  Порядок тяжёлых команд уточнить после замеров и проверки входных данных.
  Один и тот же допустимый вход должен давать научно эквивалентный результат
  локального CLI и server worker; формул в TypeScript нет.
- [~] **B3. Результат и ошибки.** CLI даёт manifest v1; worker сохраняет
  файлы, журнал и метаданные. Довести структурированные метрики,
  предупреждения, прогресс, категории артефактов и ошибки до версионированного
  контракта. Крупные файлы не складывать в PostgreSQL; пустой выход не успех.

### C. API и личный кабинет (P1; по срезам параллельно с B)

- [~] **C1. Каждая открытая возможность:** DTO в `packages/contracts`,
  серверная валидация, ownership и Swagger, типизированный `api-client`,
  форма и детали в web. `/api/calculations/kinds` должен сообщать реальную
  доступность и причину отказа, а не обещать невыполнимый сценарий.
- [~] **C2. Кабинет как рабочее место.** Уже есть запуск, выбор dataset,
  история, отмена и ссылки. Нужны пагинация/поиск, повтор с зафиксированными
  входами, сравнение, просмотр метрик/изображений/3D/таблиц по типу,
  истёкшие signed URL. Группировка в проекты — отдельная спецификация/миграция.
- [ ] **C3. Зависимые расчёты.** Пользователь выбирает свои версии входов и
  upstream jobs; API проверяет совместимость, порядок `mesh → seabed build
  → render/adapt → adaptive/validate`, статус и права каждого звена. Кабинет
  показывает зависимости и частичные ошибки, не принимает чужой artifact ID.
- [~] **C4. Дизайн и доступность.** [Дизайн-система](../sdd/design-system.md) и
  [срез 0007](../sdd/features/0007-design-system-adoption.md) частично внедрены.
  Остались контраст/клавиатура на всех маршрутах, 200% zoom, screen reader,
  мобильная визуальная приёмка и неблокирующий просмотр тяжёлых отчётов.

### D. Автономный CLI, выпуск и эксплуатация (P0 до публичного доступа)

- [~] **D1. Дистрибутив CLI.** Документация и часть бинарников есть.
  Автоматизировать сборки/тесты macOS, Linux и Windows под поддерживаемые
  архитектуры, checksum, версию ядра, проверку работы offline и актуальные
  ссылки скачивания. Исторические выпуски — [отдельная сверка](../sdd/releases.md):
  исходные assets не считать восстановленными без SHA-256 и публикации.
- [~] **D2. Защита аккаунта.** Приглашения и trusted proxy реализованы.
  Нужны проверка email, восстановление пароля, ingress rate limit и staging-
  проверка IP-цепочки. До публичной регистрации — модель угроз и негативные
  тесты; закрытый пилот можно вести отдельно.
- [~] **D3. Production-хранение и развёртывание.** Выбран AWS S3
  `eu-central-1`, подготовлен [runbook](../sdd/deployment.md), локальные сборки
  API/web прошли 25.09.2026; часть образов закреплена digest. Нужны
  приватность bucket, signed URL, закреплённые release-образы, замена
  неподдерживаемого dev MinIO `latest`, staging smoke, backup/restore
  PostgreSQL+S3, измеренные RPO/RTO, TLS, мониторинг и оператор.
  Наличие runbook не означает выполненное развёртывание.
- [~] **D4. CI и релизные ворота.** `.github/workflows/ci.yml` и локальный
  `pnpm verify` есть; 29.09.2026 он прошёл без `TEST_DATABASE_URL`, поэтому
  три PostgreSQL suites были пропущены. Нужны подтверждённые CI/Chromium с БД,
  реальный worker/S3, Gmsh/батиметрия на отдельном стенде, негативные тесты,
  совместимость миграций, resource smoke и приёмка до публикации. Сбой pull
  dev S3-образа нельзя выдавать за зелёный тест.
- [~] **D5. Документация.** Корневой README оформлен 26.09.2026. Для каждого
  нового сценария отдельно обновлять SDD, `packages/docs/content/`, Swagger,
  справку CLI и инструкции запуска; не копировать научные материалы в SDD.

## Условие закрытия плана

Каждый научный сценарий CLI из матрицы реализован для сайта либо имеет
отдельно согласованное, проверяемое ограничение по данным, лицензии или
ресурсам с задачей на снятие ограничения. Для доступных сценариев есть
проверенный путь **локальный CLI** и **web → API → worker → Go →
PostgreSQL/S3 → кабинет** на допустимом входе. Недоступные из-за данных,
лицензии или ресурсов сценарии явно отклоняются. Версии входов/ядра и
контрольные суммы дают воспроизводимость; ошибка, отмена, timeout, чужой
доступ и восстановление после сбоя проверены. CLI устанавливается и работает
offline без аккаунта. Подтверждены CI, staging, backup/restore, лимиты и
доступность web. Каждый `[~]` переводится в `[x]` только с доказательством
проверки в спецификации; продуктовые исключения утверждаются отдельно и
отражаются в пользовательской документации.
