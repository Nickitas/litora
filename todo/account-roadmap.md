# План развития лаборатории и аккаунта Litora

Сверено с кодом 18.10.2026, development, исходный SHA 756610b и рабочие изменения.
Область: продукт, web, contracts/API и необходимые изменения хранения.
Основание: [бизнес-логика](../sdd/buisnec-logic.md),
[дизайн-система](../sdd/design-system.md), маршруты и код лаборатории.

Таблица текущего состояния ниже фиксирует реализацию, а не завершённую приёмку.
В задачах [ ] означает открытый результат, [~] — частично выполненный.
Отметка [x] требует ссылки на спецификацию и проверки конкретного среза.
История прогонов хранится в спецификациях; этот документ задаёт следующие шаги.

## Цель и разделение планов

Лаборатория /lab помогает подготовить входы, осознанно запустить расчёт,
найти результат, понять его ограничения и продолжить работу. /account отвечает
за личный профиль и безопасность. Пользователь не должен помнить UUID и
внутренние имена файлов, чтобы найти своё исследование.

Главный путь: данные → запуск → состояние → понятный отчёт → следующий расчёт.
Критерии удобства — достижимые действия, сохранённый контекст и понятное
восстановление после ошибки. Научный успех, точность и воспроизводимость
определяются данными и Go-методами, а не внешним видом карточки.

- Этот roadmap отвечает за пользовательские сценарии и приёмку экранов.
- [maintenance.md](maintenance.md) — за сквозные проверки, ресурсы, сохранность,
  поставку и доступность платформы. Не дублировать здесь инфраструктурные задачи.
- [0048](../sdd/features/0048-annual-shoreline-forecast.md) — за данные пилота,
  калибровку и научную проверку прогноза. Карту можно улучшать независимо,
  но новый горизонт прогноза не появляется от добавления календаря.

## 1. Обзор и устойчивость рабочего пути

- [ ] Получать активные jobs независимо от списка последних 100. Сейчас
  [обзор](../apps/lito-web/src/pages/account/account-overview.page.tsx) фильтрует
  useCalculations и затем оставляет три записи. Показать все допустимые активные
  задания либо явные «показано N из M» и переход к отфильтрованной истории.
  Источник M — полный ограниченный активный список или серверный агрегат.
- [ ] Разделить «данные ещё не получены», подтверждённый пустой список и
  устаревшие данные после сбоя polling. Ошибка первого запроса не сопровождается
  утверждением «Нет активных расчётов»; повтор не теряет известные результаты.
- [~] Пройти с реальным API уже реализованное восстановление сессии и модулей:
  поздний 401, временный 503/offline, две вкладки, logout, обновление web-образа.
  Временная потеря связи не означает failed job или завершённый сеанс.
- [~] Завершить ручную приёмку существующей модалки и навигации по матрице ниже;
  готовые dialog/focus/scroll-lock не планируются как отсутствующая реализация.

Приёмка первого среза: более 100 завершённых jobs и старый queued всё равно
показываются корректно; доступны все 4–5 активных заданий; ошибка первого
запроса и ошибка следующего polling различимы; фильтры истории и owner-проверка
сохранены. Достаточность существующего history API проверить до добавления
нового endpoint. Новая реализация начинается отдельной спецификацией.

## 2. Каталог всех входов и понятное хранение

Развивать существующий /lab/datasets, сохраняя различия между малым dataset,
научным upload и артефактом результата. Общее представление не объединяет их
физически и не меняет UUID или политику хранения.

- [ ] Добавить научные загрузки с ролью, паспортом, датой, размером, SHA-256 и
  состоянием. Сохранение и подготовка входа доступны без автоматического job.
  Для первого среза переиспользовать текущие DTO и upload-компоненты.
- [ ] Показать результаты собственных успешных jobs как возможные входы с
  исходным расчётом и ролью. Текущий reusable-artifacts API ограничен выборкой
  до 500: поиск по ней не называть поиском по всему архиву. Пагинацию вводить,
  когда потребуется полный каталог.
- [ ] Дать понятное продолжение работы: выбрать подходящий сценарий/роль,
  открыть форму с выбранным UUID, подтвердить параметры. Нельзя автоматически
  подставлять несовместимую роль или обещать научную совместимость файлов.
- [ ] Показывать существующие квоты и их область действия. Лимит 20 файлов/
  2 ГиБ относится к научным входам и резервациям, а не всему S3. Общий расход,
  дату удаления и вычислительную квоту показывать только после серверного
  контракта и принятой политики из A4/A6 общего плана.
- [ ] Предоставить доступное действие удаления только pending-резервации через
  существующий API. Удаление ready-входов и datasets — отдельный контракт с
  проверкой зависимых jobs, S3 и восстановления.
- [ ] Предотвратить повторное создание одного учебного примера конкурентными
  вкладками через отдельное серверное решение. Клиентское переиспользование
  Сочи уже есть; это не строгая идемпотентность. По одному SHA-256 нельзя
  молча объединять разные пользовательские паспорта/источники/лицензии.
- [ ] Семейства версий вводить только для явного сценария обновления данных.
  Сохранённый используемый файл уже нельзя перезаписать обычным upload;
  будущая версия создаёт новый UUID и сохраняет проверяемую связь с предыдущей.

Приёмка: владелец находит свой файл вне формы запуска, отличает готовый вход
от резервации и результата job, видит заявленные источники и роль. Ошибка
одного списка не маскируется пустотой остальных. Чужие UUID недоступны;
нажатие на данные само не запускает расчёт.

## 3. Зависимости, повтор и поиск

### Источники и следующие расчёты

- [~] Переиспользование собственных успешных артефактов и защита от удаления
  источника уже работают. Добавить в детали списки «Использует результаты» и
  «Используется в расчётах» с owner-scoped API и ограничением объёма.

- [ ] Для отказа в удалении дать понятный переход к своим зависимым jobs.

- [~] Повтор формы уже есть. Добавить серверно проверяемое происхождение
  нового запуска и сохранять его после reload. Связь «повторяет» не равна
  зависимости от входного артефакта; её влияние на удаление определить отдельно.
- [ ] Объяснять текущую версию ядра и исходные core/method/schema до повтора.
  При неизвестной старой версии показать отсутствие данных, а не подставить
  текущую. Название действия — повтор параметров на доступном ядре;
  «точное воспроизведение» требует отдельной инфраструктуры из A3 общего плана.

Приёмка: цепочка mesh → build → render/adapt проходит по собственным UUID,
ссылки объясняют происхождение и запрет удаления; повтор создаёт новый UUID,
не отправляется автоматически и не заменяет недоступный вход демо-файлом.

### Названия и заметки

- [ ] Добавить редактируемое название job и простую текстовую заметку:
  ограниченная длина, runtime-валидация, безопасный текст, owner-scoped изменение.
  По умолчанию остаются название сценария и дата; старые jobs не требуют
  искусственного массового переименования.
- [ ] Добавить серверный поиск по названию вместе с текущими фильтрами и
  cursor-пагинацией. UUID остаётся доступным для точного поиска и поддержки.
  Фильтр не применяется только к уже подгруженным строкам.
- [ ] После проверки частотных сценариев решить, нужны ли избранное и
  сохранённые фильтры. Не вводить несколько одинаковых способов организации
  раньше понятного названия и заметки.

Приёмка: два одинаковых сценария различимы без UUID; название сохраняется
после reload и доступно только владельцу; поиск находит результат за пределами
первой страницы, ошибки не теряют текст заметки.

  owner, название/цель, ссылки jobs/inputs и правила удаления/экспорта.
- [ ] Если потребность подтверждена, реализовать личную группировку с
  серверной проверкой всех связей. Проект не выдаёт доступ другим людям и
  не является обязательным условием запуска, повтора или просмотра отчёта.

### Отложено до конкретной потребности

- Отдельное меню «Результаты», дублирующее историю, и /lab/storage без API
  реального расхода/retention. Сначала добавить нужное представление в готовые разделы.
- Сравнение 3–4 запусков и экспорт проекта до появления практического сценария.
- Центр уведомлений, email/push/webhook до решения, какое действие они
  помогают совершить. Текущие статусы/polling не требуют новой системы событий.
- Команды/организации, роли экспертов, оплата и MFA без отдельной модели прав
  и угроз. Наличие role=admin в БД не даёт административного интерфейса.
- Исторический registry ядра и кнопка точного rerun до принятой политики
  неизменяемых входов, версий и хранения; существующий повтор параметров остаётся.

## Навигация и визуальные требования

Основные рабочие адреса остаются /lab, /lab/calculations,
/lab/calculations/:jobId, /lab/datasets, /lab/shoreline и отдельный /account.
Новый расчёт — действие с диалогом. Новые пункты меню появляются вместе с
работающим сценарием; /lab/projects, /lab/storage и /account/settings сейчас
не являются существующими маршрутами.

Сейчас lab shell использует боковую навигацию 240 px на desktop и горизонтальный
список разделов на mobile; глобальная шапка имеет собственное раскрываемое меню.
План не объявляет мобильный Sheet уже реализованным. Приёмка проверяет фактические
переходы, фокус и отсутствие потери действий; изменение композиции проводится
отдельно по дизайн-системе и подтверждённой проблеме.

- Сохранять shadcn radix-nova, Radix, Tailwind 4, Lucide и semantic tokens
  «Чёрное море». Системный HTML сохраняет семантику; интерактивные элементы
  оформляются общими примитивами. Логику формул не переносить в TypeScript.
- Основной результат и следующее действие доступны до технических деталей.
  Паспорт/хеши/журнал раскрываются по необходимости; декоративные карточки не
  заменяют содержание, уведомление появляется только по проверенному факту.
- Dialog: центрирование, scroll-lock сайта, собственная прокрутка длинной
  формы, Tab/Shift+Tab, Escape, возврат фокуса, общий крестик, лёгкая анимация
  и reduced motion. Эти свойства уже реализованы; их нужно проверять.
- Фильтры не теряют контекст при возврате из деталей. Длинная таблица имеет
  доступную ручную подгрузку наряду со scroll-trigger и понятную ошибку.
- Обе темы, 360 px, 200% zoom, видимый focus и экранный диктор входят в
  приёмку. Статус понятен без цвета; график имеет легенду, единицы и доступную
  текстовую альтернативу. Новые проценты готовности требуют реальной метрики.

## Единая матрица приёмки

| Экран/путь | Обязательные проверки |
| --- | --- |
| /lab | Старый активный job, полные активные данные, явный предел показанной выборки, ошибка/пустота/устаревание, последний результат |
| Новый расчёт и повтор | Полный цикл фокуса/закрытия, длинная форма, недоступный вход, ошибка отправки с сохранением полей, защита от двойного клика |
| История | Серверные фильтры и cursor, возврат/URL, ошибка следующей страницы без потери строк, чужой UUID, сравнение двух результатов |
| Детали | Быстрые переходы A → B без смешивания, старый неполный паспорт, свежие signed URL, отдельная ошибка файла, экспорт без секретов |
| Наборы данных | Независимые ошибки списков, свои паспорта, роли и статусы, поиск в заявленной области, явное действие перед созданием/удалением |
| Динамика берега | Различие наблюдения/модель, пропущенные даты и годы, переход между частями, сохранение контекста карты, отказ API и длинный ряд |
| Аккаунт | Только собственные данные; реально доступные действия отделены от будущих; сохранение/ошибка после добавления редактирования |
| Сквозные состояния | Временный 503/offline и восстановление; две вкладки и logout; reload; старый web-модуль после обновления релиза |

Для каждого прохода фиксировать SHA, маршрут, браузер, тему, ширину/zoom,
действие, ожидаемый и фактический результат, ссылку на тест/дефект. Chromium E2E
на mock API не заменяет реальную цепочку; Safari/Firefox, экранный диктор и
staging отмечаются отдельно, а не считаются проверенными автоматически.

## Правила реализации и проверки

Каждый кодовый срез начинается спецификацией в sdd/features/ по
[шаблону](../sdd/templates/feature.md). Для изменений API порядок:
contracts/runtime-валидация → API/worker/Go → api-client → web/Swagger →
пользовательские документы. Нужная миграция новая, опубликованные не меняются.
Владение проверяется сервером для каждой сущности и связи.

Документирование само по себе не требует новых endpoint, таблиц, зависимостей
или UI-кнопок. Для проверки roadmap достаточно ссылок, согласованности с кодом
и git diff --check. Для кода — пропорциональные проверки из AGENTS/SDD и
pnpm verify; web дополнительно проверяется браузером и lint. Auth/jobs/S3
проверяются на выделенном тестовом окружении, не на production.

После реализации фиксировать отдельно код, автоматические проверки, ручную
приёмку и фактический выпуск. Экспорты/логи не включают токены и signed URL.
Открытые вопросы retention, публичных прав, доставки email и точного
воспроизведения остаются отдельными решениями; они не блокируют просмотр
своих уже существующих данных и улучшение текущих экранов.
