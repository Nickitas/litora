# lito - правки по user-flow и результату работы

## План исправлений

Составлен 21.10.2026 после сверки замечаний с кодом и SDD.

### Уточнения пользователя от 21.10.2026

- Сочи, Геленджик и Турция были примерами, а не ограничением географии.
  По уточнению пользователя начальный реестр расширен до 24 районов разных
  частей Чёрного моря: 8 первой очереди и 16 второй. Состав и задачи каждого
  района приведены в спецификации 0062; можно добавлять другие полезные участки.
  Точные ROI и пригодность источников проверяются отдельно.
- Нужна точность, достаточная для исследований будущих пользователей. Численный
  порог пользователь не задавал: на шаге 01 предложена проектная цель RMSE
  положения линии до 10 м с независимой проверкой каждого пилотного сегмента.
  Это цель для научного согласования, не уже измеренная точность системы.
- Выбрана сразу автоматическая цепочка получения снимков и обработки CoastSat.
  Ограничиваться сценарием ручного импорта как целевым решением не планируем.
- Желаемый горизонт прогноза — до одного года. Допустимость такого горизонта
  и его погрешность предстоит подтвердить научной проверкой.

### Порядок работы

- Работаем в `development`. Один номер — одно изменение с самостоятельным
  результатом и приёмкой. Связанные правки contracts/API/Go/web могут входить
  в один шаг, если обслуживают одну функцию. Независимые улучшения не примешиваем.
- Перед реализацией шага фиксируем границы, риски и проверяемые требования
  в соответствующей спецификации `sdd/features/` по
  [шаблону](../sdd/templates/feature.md). Этот файл остаётся очередью работ.
- Начинаем следующий шаг после проверки предыдущего; зависимые задачи ждут
  решения своих вопросов. Галочку ставим по результату проверки, а не написания кода.
- Реальные исходные данные не гарантируют точность любого расчёта. Для каждого
  сценария нужны подходящие масштаб, даты, разрешение и проверка метода.
  Ограничения переносим в паспорт и справку, сохраняя существенные предупреждения
  перед запуском. Простое переименование демонстрации в исследование не подходит.
- Существующие пользовательские наборы, задания и результаты сохраняем.
  Коммиты и push в этот план не входят: коммит делает пользователь.

### Что уже есть и на что опираемся

- Малые датасеты уже ограничены API: 100 на пользователя, GeoJSON до 65 536 байт,
  LineString из 2–500 точек в EPSG:4326. При загрузке файла уже есть редактируемое
  название и автозаполнение из имени файла. Для сохранения встроенного примера
  такого редактирования сейчас нет.
- Карточки датасетов показывают паспорт, но не открывают просмотр геометрии.
  Публичный контроллер датасетов сейчас предоставляет список и создание.
- Полный контур уже есть: `apps/lito-cli/data/coastline/black-sea.geojson` и его
  паспорт MarineRegions MRGID 3319. Размер по паспорту — 299 701 байт. Это граница
  морского района с ограничениями применимости, включая границы акватории;
  считать её точной съёмкой всей береговой линии нельзя.
- Для крупных научных файлов уже существует отдельный реестр и приватное S3;
  есть сценарий `coastline_region` для выделения участка. Полный контур не нужно
  втискивать в малый датасет ценой неоговорённого упрощения.
- Динамика находится на `/lab/shoreline`; в исходных замечаниях для неё повторён
  адрес `/lab/datasets`. На странице соседствуют наблюдения GeoJSON и состояния
  CERC, включая встроенный семисуточный пример. Состояние модели не равно снимку.
- Импорт подготовленных наблюдений CoastSat уже реализован; сам CoastSat внутри
  Litora не запускается. Годовой прогноз в
  [0048](../sdd/features/0048-annual-shoreline-forecast.md) остаётся draft:
  аудит данных и калибровка не означают готовый проверенный прогноз.
- Новая форма уже получает список сценариев API. Для рисунков 3 и 5 есть
  `seabed_render`, для рисунка 4 — `seabed_adapt` и
  [сценарии переходов](../sdd/features/0060-seabed-figure-workflows.md).
  Требуется понятный выбор результата, а не ещё один независимый блок пресетов.

### Открытые вопросы и проверяемые допущения

1. Какие исследовательские величины и погрешности принимаем для пилотных районов?
   На шаге 01 предложены сценарии, единицы и цель RMSE ≤10 м для положения линии.
   Их научное согласование и подтверждение независимыми данными ещё требуются;
   допустимая ошибка годового прогноза определяется отдельно на шаге 27.
2. Требуется ли именно подробная береговая линия всего Чёрного моря, включая
   острова, лиманы и проливы, или достаточно обзорного контура и подробных участков?
   План сохраняет 100 малых LineString по 64 КиБ; полный исходник живёт отдельно.
   Дополнительный существующий лимит 500 точек не меняем без отдельного решения.
3. Для выбранной автоматической цепочки CoastSat предстоит определить доступный
   Google Earth Engine project, квоты и условия использования для типа проекта.
   Наличие нужных наблюдений Чёрного моря в готовых каталогах пока не подтверждено.
4. Под отказом от демонстраций понимаем удаление пользовательских сценариев,
   сохраняя синтетические данные только в автоматических тестах? Сохранение
   прежних пользовательских результатов заложено в план, их удаление не требуется.

Ответы можно уточнять до соответствующего шага. Выбранные CoastSat и годовой
горизонт зафиксированы выше; отсутствие других ответов не означает согласия
на платный сервис, дополнительные интеграции или изменение лимитов.

### Проверки каждого изменения

- Документы: согласованность с кодом, существование локальных ссылок,
  `git diff --check`. Обновления SDD и пользовательских методик идут вместе
  с изменением поведения и остаются в своих каталогах.
- Приложение: `pnpm verify`; для Go дополнительно `go vet ./...`, при изменении
  конкурентности — `go test -race ./...`. При изменении опубликованного
  Go-метода повысить его ревизию и проверить манифест и путь worker → API → web.
- API, jobs и S3: отрицательные проверки чужих ресурсов, лимитов и ошибок;
  `pnpm test:integration` только в отдельном локальном/тестовом окружении.
- UI: проверять изменённый сценарий на мобильном экране, в обеих темах,
  с клавиатурой, включая loading, empty, ошибку, отмену и отсутствие доступа.
- Научные данные и отчёты: сохранять происхождение, версию, CRS, единицы,
  контрольные суммы и ограничения; сопоставлять вычисленный результат с эталоном.
  Успешная сборка или HTTP 200 не заменяют эту проверку.
- В завершении шага записывать команды и результаты, пропущенные проверки,
  оставшиеся ограничения и проверять diff на секреты/крупные артефакты.
