# План приведения `infra/` в порядок

Статус: план и журнал работ на 18.10.2026. Отмеченные пункты подтверждены только
указанными ниже проверками; это не означает production-приёмку.

## Что есть сейчас

- `compose.yaml` — локальные PostgreSQL, MinIO из зафиксированных исходников, API,
  обычный и тяжёлый worker, web. `compose.local.yaml` задаёт локальные имена
  контейнеров `lito-infra-*`, не меняя Compose-проект и существующие volumes.
- `postgres/init/001_schema.sql` … `016_observed_shoreline_series.sql` — история
  миграций. API и worker применяют их по порядку под advisory lock и записывают
  результат в `schema_migrations`. Отдельного `postgres-init` больше нет.
- Production Compose пока находится в `sdd/examples/compose.production.yaml` как
  шаблон; порядок развёртывания и восстановления описан в `sdd/deployment.md`.

## P1 — убрать дублирование и стабилизировать локальный стенд

- [x] Оставить один механизм миграций: API/worker применяют все SQL через
  `DatabaseService.initialize()`, а `postgres-init` удалён из локального Compose.
  Зависимость API переключена на здоровый PostgreSQL, инструкция обновлена;
  опубликованные SQL-файлы не менялись. На отдельном временном PostgreSQL без
  volume: чистая БД получила 16 миграций; на её копии повторный запуск не изменил
  число миграций, объектов схемы и контрольную запись пользователя. Проверены
  `docker compose ... config --quiet` с профилем `app` и typecheck API.
  Откат конфигурации: вернуть только сервис `postgres-init` и прежний
  `depends_on` API; volumes и уже применённые миграции не откатывать.
- [x] Проверить совместный запуск API и standard worker на изолированном
  одноразовом dev-стенде без volumes: PostgreSQL применил 16 миграций, API
  вернул `200 /api/health`, worker сообщил о готовности. После остановки и
  повторного запуска API и worker снова стартовали, `/api/health` вернул 200,
  число миграций осталось 16. В тестовой БД не было заданий. Временные
  контейнеры остановлены; исходные volumes не затронуты. Это проверка
  эквивалентных сервисов, но не буквальный запуск `pnpm infra:up`.
- [x] Проверить обычный локальный Compose после резервных копий volumes
  PostgreSQL и MinIO. Копии `litora_p1_backup_postgres_20261018` и
  `litora_p1_backup_minio_20261018` побайтово совпали с остановленными
  исходниками; они оставлены в Docker для локального отката (не off-host backup).
  `pnpm infra:up` поднял оба сервиса healthy; `pnpm dev:api` вернул
  `200 /api/health`, `pnpm dev:worker` сообщил о готовности. Новый MinIO
  видит 23 прежних объекта; локальный smoke подтвердил bucket, загрузку,
  скачивание и signed URL. После остановки и повторного запуска API и worker
  снова готовы, число миграций осталось 16. До запуска worker в БД были только
  четыре `succeeded` job и восемь уже `deleted` записей на удаление;
  тестовые задания не создавались. Остановленный orphan `infra-postgres-init-1`
  удалён без удаления его анонимного volume; повторный `pnpm infra:up` прошёл
  без предупреждений и пересоздания контейнеров. Общий `pnpm verify` прошёл.
  Откат при несовместимости данных — только из оставленных копий после остановки
  сервисов; запускать старый MinIO на изменённом volume нельзя.
- [x] Заменить локальный `minio/minio:latest` на сборку MinIO из официальных
  исходников релиза `RELEASE.2025-10-15T17-29-55Z` с проверкой commit SHA и
  фиксированными digest базовых образов. Пользователь выбрал этот dev-путь;
  лицензия AGPLv3 и ограничение «не production» описаны в ADR-023. На пустом
  временном хранилище проверены bucket, upload, download и signed URL. На
  временной копии существующего volume новый образ прочитал 1 bucket и 23 объекта,
  S3 smoke тоже прошёл; копия удалена, оригинальный volume не переключался.
  Финальный образ после коррекции ReleaseTag собран и повторно прошёл S3 smoke.
  Перед запуском Compose на оригинальном volume нужна локальная копия для отката
  по `sdd/development.md`; это не заменяет off-host backup. Локальный image ID
  зависит от платформы и сборки, а production по-прежнему использует AWS S3.
  Откат: остановить новый MinIO и восстанавливать данные из проверенной копии
  отдельным решением; запускать старый образ на уже изменённом volume нельзя.
- [x] Добавить в CI проверку итогового локального Compose (`compose.yaml` вместе
  с `compose.local.yaml`, включая профили `app` и `heavy`) и тест миграций на
  пустой и повторно используемой тестовой БД. Локальный прогон
  `test:migrations` на одноразовом PostgreSQL прошёл: 16 файлов, повторный запуск
  не изменил схему и контрольную запись. Скрипт создаёт и удаляет только свою
  БД `litora_test_migrations_*` на localhost; запуск GitHub Actions после push
  в `main` ещё не проверен. Откат: убрать шаги CI и скрипт; пользовательские БД
  и volumes при этом не меняются.

## P2 — готовность к эксплуатации

- [ ] Превратить описанные в `sdd/deployment.md` резервное копирование и
  восстановление PostgreSQL + S3 в проверяемую процедуру для staging: расписание,
  off-host копия, контроль свежести и регулярный restore drill. Не выполнять
  `down -v`, очистку bucket или восстановление поверх действующей БД.
  Первый шаг: добавлены `scripts/backup-manifest.mjs` и
  `apps/lito-api/scripts/backup-s3-inventory.mjs`; `pnpm verify` включает
  позитивные и негативные backup-тесты. Манифест v2 фиксирует SHA-256/размер
  дампа, CSV и перечня объектов; S3-проверка сверяет все ключи и размеры в
  backup-prefix, включая пагинацию. Runbook показывает последовательность
  создания и проверки. Локальный smoke на одноразовом MinIO с тремя объектами
  прошёл. Это **частичное** выполнение: реальная off-host копия,
  расписание, контроль свежести в мониторинге и restore drill на staging ещё
  не проверены. Требования и риски: `sdd/features/0051-staging-backup-verification.md`.
- [ ] Сделать наблюдаемыми очередь и worker: число/возраст `queued`, устаревший
  heartbeat, ошибки заданий, расход диска и отсутствие свежего backup. Проверять
  не только `/api/health`, но и прохождение тестового задания до результата.
  - [x] `queue:status` показывает очередь и heartbeat job; worker теперь
    регистрирует собственный heartbeat, включая простой. Оператор может требовать
    присутствие выбранного профиля через `--require-worker`. В JSON v2 есть
    агрегат failed jobs за 24 ч. Миграция и диагностический SQL проверены на
    одноразовом PostgreSQL. Требования: `sdd/features/0053-worker-presence.md`.
  - [ ] Настроить внешние алерты, пороги диска и свежесть **off-host** backup;
    проверить stop/restart worker и контрольный расчёт на staging. До этого
    наблюдаемость в целом не принята.
- [ ] Проверить остатки временных файлов после аварийного завершения
  `worker-heavy` и ввести ограниченную очистку scratch-volume
  `litora_heavy_jobs` с защитой активных заданий и входных файлов.
  - [x] Heavy worker помечает scratch до записи входов; `scratch:cleanup`
    делает dry-run и разрешает ограниченное удаление только старых завершённых
    jobs после сверки с БД, подтверждения корня и отсутствия активной очереди.
    Локальные тесты имитируют аварийный остаток и негативные случаи.
  - [ ] Проверить реальный сбой, состав volume и очистку на staging. До этой
    приёмки родительский пункт остаётся открытым. Runbook: `sdd/deployment.md`,
    требования: `sdd/features/0052-heavy-scratch-cleanup.md`.
- [ ] После staging-приёмки решить, должен ли рабочий production Compose
  переехать из `sdd/examples/` в `infra/`. Если переносить — одновременно
  обновить `scripts/deploy-prebuilt.sh` и runbook; инженерные правила остаются
  в `sdd/`, публичная документация — только в `packages/docs/content/`.

## Не делать ради «уборки»

- Не удалять старые миграции, `compose.local.yaml` или volumes с данными.
- Не добавлять Redis, новый брокер/ORM или production MinIO без измеренной
  потребности и отдельного архитектурного решения.
- Не считать локальные default-пароли, исходный MinIO и открытые localhost-порты
  готовой production-конфигурацией.

Работать по одному пункту: проверить текущий diff, сформулировать способ отката,
изменить код и документацию, выполнить проверки, затем отметить результат здесь.
