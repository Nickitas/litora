# Восстановление исторических релизов CLI

Проверено 25.09.2026: публичный GitHub API возвращает `404` для
`Nickitas/litora-cli` и `Nickitas/litora-web`; у `Nickitas/litora` список
Releases пуст. `404` не доказывает удаление репозитория: он также возможен для
приватного репозитория без доступа. Пока доступ и исходные release assets не
подтверждены, нельзя заявлять, что архивные релизы перенесены.

## Что сохранилось локально

В локальном Git есть теги `v1.0.0`, `v1.0.1`, `v1.2`, `v2.0` старого CLI.
Они указывают на **отдельную историю до монорепозитория**, а не на commits
`main`/`development`. Не перемещать их без отдельного решения: это разрушит
связь тега с исходным кодом того выпуска. `v1.0.1` не показан на сайте, но
также требует инвентаризации.

В `apps/lito-web/public/downloads/` находятся четыре бинарника v2.0.
Их текущие SHA-256 зафиксированы в `apps/lito-web/src/shared/config/releases.json`
и проверяются командой `pnpm test:web`. Это доказательство целостности
**локальных файлов**, но не доказательство совпадения с прежними GitHub assets.

## Порядок переноса

1. Владелец проверяет, доступны ли прежние репозитории под учётной записью
   GitHub. Если да, выгружает **для каждого тега** текст релиза, дату публикации,
   список assets, размеры и SHA-256 оригиналов. Оригинальные assets хранить
   отдельно до завершения сверки; не заменять их пересобранными бинарниками.
2. Если прежних Releases уже нет, найти независимый архив исходных вложений.
   При отсутствии архива явно пометить выпуск как «исходники по тегу сохранены,
   оригинальные assets не восстановлены». Не выдавать четыре файла сайта за
   оригиналы старого Release без сравнения хешей.
3. Сверить Git-теги и полный commit SHA, решить, публиковать ли архивные теги
   с их исходной историей в новом репозитории. Перед `git push` убедиться, что
   такое же имя тега ещё не занято в `litora`, и не делать force для тегов.
4. Для каждого подтверждённого выпуска создать GitHub Release в `litora` с
   верным тегом, исходным текстом и **только проверенными** вложениями. Если
   исходных вложений нет, писать это в Release notes, не создавать фиктивный
   download. Публикация изменяет внешний репозиторий и проводится отдельно от
   обычного локального коммита.
5. Сверить опубликованные URL, SHA-256 загруженных assets и downloads на сайте.
   Только после этого обновить `releaseUrl` в web с `null` на новый адрес.
   Проверить ссылки для v1.0.0, v1.0.1, v1.2 и v2.0 вручную и в CI.

Текущая страница `/releases` честно ведёт к локальной загрузке v2.0, но не
ссылается на несуществующие старые Releases. Упоминание «архивный релиз» не
является обещанием доступного бинарника.
