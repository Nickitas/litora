# Бизнес-логика Litora

Статус: фактические возможности на 29.09.2026 и явно отделённый план развития.
Litora помогает исследовать береговую линию и рельеф дна Чёрного моря, запускать
воспроизводимые вычисления и хранить результаты. Это исследовательский инструмент,
не автоматическое заключение о безопасности сооружения и не гарантированный прогноз.

## 1. Пользователи и права

| Пользователь / персона | Потребность | Реальные права сейчас |
| --- | --- | --- |
| Гость сайта | Прочитать методики, изучить проект | Публичные страницы; нет личных заданий |
| Зарегистрированный пользователь | Запустить расчёт, сохранить и скачать отчёт | Только собственные jobs и артефакты |
| Исследователь / инженер | Проверить гипотезу и качество исходных данных | Та же роль user; это персона, не отдельная роль БД |
| Студент / преподаватель | Разобрать демонстрацию, сопоставить методы | Та же роль user; демо явно маркируется |
| Пользователь standalone CLI | Автоматизация и сложный локальный анализ | Нет аккаунта, БД или S3; собственная файловая система |
| Оператор платформы | Обновления, восстановление, наблюдение | Через инфраструктуру; административного кабинета нет |

В БД допустимы `user/admin`, но специальный admin API/RBAC ещё не реализован.
Организаций, команд, платных тарифов, общего доступа и публичных ссылок на проекты
нет. Signed URL — ограниченный по времени доступ к отдельному файлу, а не shared project.

## 2. Возможности: что уже есть

- Регистрация именем, email, паролем и одноразовым приглашением; вход, обновление сессии, выход, получение профиля.
- Лаборатория: `/lab` — обзор и модальное окно выбора сценария и
  запуска, `/lab/calculations` — история с кратким просмотром,
  `/lab/calculations/:jobId` — детали и отмена, `/lab/datasets` — наборы данных,
  `/lab/shoreline` — визуализация динамики берега. Два завершённых расчёта
  одного типа и версии result schema можно открыть рядом без вычисления новых
  научных метрик. `/account` — отдельная заготовка личного профиля с именем и
  email без редактирования. Все эти маршруты доступны только после авторизации;
  прежние вложенные адреса `/account/*` перенаправляют в лабораторию.
- Из деталей своего расчёта можно открыть новую форму с сохранёнными параметрами.
  Перед отправкой владелец меняет их и явно заменяет недоступные входы; новая
  задача использует текущую версию ядра, не исторический бинарник.
- Загрузка малого GeoJSON-контура для dimension с паспортом источника и лицензии;
  пользователь видит и запускает только собственные наборы. На `/lab/datasets`
  открыт каталог 24 подготовленных картографических фрагментов с превью, поиском,
  ограничениями и ссылками на OSM. Явное сохранение под своим именем создаёт
  приватную копию в действующей квоте и запускает проверку геометрии Go.
  Точность положения независимо не подтверждена; временных рядов в каталоге нет.
  В форме нового расчёта пока также можно
  использовать пример Сочи (OpenStreetMap, ODbL), который при первом запуске
  сохраняется как приватный набор; это не пользовательская съёмка.
- Асинхронное выполнение с ограничениями времени и ресурсов, статус и текст ошибки.
- На странице наборов доступны полный исходник MarineRegions MRGID 3319 и
  собственные линии успешных `coastline_region`. Полный исходник сохраняется
  явным действием в приватный реестр научных файлов через серверный каталог,
  с квотой 20 файлов/2 ГиБ и повторным использованием своей копии по паспорту.
  Граница морского района не объявляется береговой съёмкой. Выделение открывается
  по UUID своего готового источника после проверки Go; линии остаются артефактами
  своего расчёта в S3 и доступны для следующих сценариев без ручной загрузки.
- Небольшая сводка метрик, просмотр SVG и скачивание результатов из приватного S3.
- Скачивание паспорта метаданных расчёта JSON v1 из собственных деталей job;
  без файлов, signed URL и технической командной строки. Это не точное
  воспроизведение исторической версии ядра.
- Swagger `/api/docs`, схема `/api/docs-json`; health БД и S3 `/api/health`.
- Самостоятельный CLI с большим набором научных сценариев и общая документация.

`/api/releases/latest` пока возвращает заглушку без файлов: автоматизированный
каталог релизов CLI не считать реализованным.

## 3. Сессии

Email нормализуется в lowercase и уникален. Имя 1–100 символов, пароль 10–128;
неизвестные поля запроса отвергаются. Пароль хешируется Argon2id; в API его нет.
Новая регистрация требует `invitationCode`: оператор выпускает ключ на 1–720 часов
(default 168) и может отозвать его по UUID. В БД только SHA-256 ключа. Погашение,
создание пользователя и сессии — одна транзакция; действующие аккаунты не меняются.
Это ограничение доступа к пилоту, не проверка email. Admin UI и рассылки нет.
Access/refresh — случайные opaque tokens, **не JWT**. В БД хранятся SHA-256 токенов.

Access token действует 15 минут, хранится в памяти web. Refresh — HttpOnly cookie
`litora_refresh`, `SameSite=Strict`, `Path=/api/auth`; `Secure` включается в production.
Refresh ротируется, срок сессии ограничен 30 днями от создания, а не продлевается
на 30 дней при каждом запросе. Logout отзывает сессию. Перезагрузка страницы
восстанавливает вход через refresh; истёкшая сессия возвращает на вход.
Web обновляет access-token до истечения срока и повторяет запрос со старым токеном
после успешного refresh. Параллельные вкладки согласуют ротацию без записи токенов
в localStorage/sessionStorage. Только подтверждённый 401 refresh означает
завершение сессии; временная ошибка сети/API допускает повтор проверки без
ложного сообщения об истечении. Детали и ограничения: [срез 0045](features/0045-auth-session-recovery.md).

Ограничение auth: 30 попыток/минуту на IP; за текущим reverse proxy это может быть
общий IP proxy. Нельзя обещать полноценный per-user anti-abuse. Проверка Origin
допускает настроенные `WEB_ORIGIN` и `API_ORIGIN`; отсутствие Origin допустимо для CLI.
Нет email verification, password reset, MFA и управления списком устройств.

## 4. Сущности и связи

```text
users 1 ─── N auth_sessions
  │
  ├── 1 ─── N datasets ─── приватный объект S3
  └── 1 ─── N calculation_jobs 1 ─── N calculation_artifacts ─── объект S3
                       │
                       ├─────── 0..1 dataset
                       └─────── 1 ─── N calculation_events
```

| Сущность | Значимые данные и ограничения |
| --- | --- |
| users | UUID, email, password_hash, display_name, role, временные метки |
| auth_sessions | Владелец, hashes токенов, сроки access/refresh, revoked_at |
| datasets | UUID, владелец, имя, заявленные источник/лицензия, CRS/единицы, точки, размер, SHA-256, приватный object_key |
| calculation_jobs | UUID, user_id, kind, status, input, result_summary, core_version, command_line, worker_id, heartbeat, ошибки и даты |
| calculation_artifacts | job_id, filename, category, bucket/object_key, content_type, size_bytes, sha256, metadata |
| calculation_events | job_id, event_type, payload, время; технический журнал, не полноценный неизменяемый аудит |
| auth_rate_limits | Ключ, начало окна, число попыток |
| registration_invitations | UUID, code_hash, сроки, used_at/used_by, revoked_at; без исходного ключа |
| schema_migrations | Имя применённого SQL и время; инфраструктурный учёт |

Владелец нового HTTP-задания обязателен и берётся из сессии, не из DTO пользователя.
У старого импорта `user_id` может быть NULL: такие jobs не видны в кабинете. Удаление
пользователя на уровне FK обнуляет владельца jobs; продуктового удаления аккаунта
пока нет. Нельзя самовольно считать этот FK политикой удаления персональных данных.

Связь artifact → S3 логическая, не внешний ключ. Текущий ключ worker:
`users/{jobId}/{relativePath}`; слово users не означает наличие userId в пути.
Импортёр использует `calculations/{jobId}/{relativePath}`. Права определяются БД,
а не угадыванием ключа. Уникальная пара bucket/object_key предотвращает дубликат реестра.

В формах `seabed_adapt` и `seabed_compare_adaptive` есть пресеты параметров
архивной статьи для рисунков 4, 5 и 6–7. Пресет рисунка 5 дополнительно
включает AI-01 и сборку SVG из трёх его карточек. Это только заполнение
`input`: выбор собственных научных файлов, ресурсное разрешение и запуск
остаются отдельными действиями. Пресет не удостоверяет совпадение SVG.

Пример: `POST /api/calculations` с `{ "kind": "erosion", "input": { "steps": 3 } }`.
Пользовательский набор создаётся через `POST /api/datasets`: только `EPSG:4326`,
`degrees`, 2–500 пар `[долгота, широта]`, до 64 KiB. API фиксирует заявленные
источник/лицензию и SHA-256; успешная загрузка не подтверждает научную пригодность.
API не принимает путь, CLI-флаги, URL, произвольный shell или научные параметры,
которых ещё нет в контракте. Каталог сценариев доступен через `/api/calculations/kinds`.
Научные файлы резервируются через `POST /api/scientific-inputs` и загружаются
потоком через `PUT /api/scientific-inputs/:id/content`; допускаются только
собственные готовые UUID соответствующей роли. Метаданные источника и лицензии
заявляет пользователь; научную совместимость проверяет Go, не API.
До ready проверяется фиксированная структура файла по роли и предел размера.
Точные схемы и описания доступны через `GET /api/scientific-inputs/formats`
и скачиваются в форме загрузки. Файлы с неизвестными полями, типами, версиями,
неверными координатами, оборванными таблицами или MSH отклоняются до S3.
Структурная пригодность не подтверждает научную совместимость.

Сценарий `coastline_region` принимает west/south/east/north и необязательный
`coastlineInputId`. Область выбирается по двум углам на карте или координатами
в пределах Чёрного моря. Go выделяет все самостоятельные линии без упрощения
и искусственного соединения; отдельные GeoJSON можно использовать в размерности
и CERC. Для CERC нужны свои локальные волны/глубины, для Gmsh — замкнутая
морская область. Встроенный полный контур и собственный источник доступны через
API preview; ошибка своего источника не переключает карту на встроенный.
Источники для скачивания и требования преобразования перечислены в справочнике
«Участки Чёрного моря, форматы и источники данных». Новая сетевая интеграция
не вводится.

Для продолжения цепочки API также предлагает UUID распознанных артефактов
собственных успешных расчётов (`GET /api/scientific-inputs/reusable-artifacts`).
Один и тот же UUID в поле входа может означать загруженный научный файл или
артефакт; API и worker разрешают его только при совпадении владельца, роли,
статуса и приватного bucket. В S3 копия не создаётся, исходный успешный
результат нельзя удалять без проверки зависимых заданий.

Формат и состав конкретных файлов определяет manifest. Не строить UI на позиции
файла в массиве. Новые имена/метрики версионировать и документировать до потребителя.
Демонстрация эрозии не прогноз годового размыва, обзорная схема не точная съёмка.

## 6. Зависимости научных возможностей CLI

Это концептуальные зависимости данных, **не реализованный DAG оркестратора**:

| Возможность CLI | Нужные данные / зависимость |
| --- | --- |
| source / подготовка контура | Источник, лицензия, CRS, геометрия берега |
| dimension | Валидная геометрия, масштабы анализа |
| map | Контур и область отображения |
| mesh | Контур, разрешение; Gmsh для соответствующего генератора |
| seabed | Батиметрия, область, nodata, интерполяция, сетка |
| erosion | Берег, волновой режим и параметры модели |
| calibrate-cerc | Наблюдения и условия калибровки модели |
| all | Набор CLI-сценариев и их prerequisites |

Не все эти возможности доступны через HTTP. Полные GEBCO-наборы и Gmsh не входят
автоматически в среду текущего worker. Данные карты, сетки, рельефа и эрозии нельзя
соединять без проверки совместимости CRS, единиц, разрешения, времени и источника.
Развёрнутое научное объяснение методов остаётся в материалах для читателя сайта;
здесь зафиксированы только зависимости для планирования функций.

## 7. Жизненный цикл расчёта

```text
queued ──захват worker──> running ──сохранены результаты──> succeeded
   │                        ├──ошибка / timeout / stale──> failed
   └──отмена──> cancelled <─┘ отмена владельцем
```

- API в транзакции ограничивает пользователя пятью `queued/running` jobs. При
  превышении действует лимит, а не тихое удаление старого расчёта.
- Claim через `FOR UPDATE SKIP LOCKED`; один worker-процесс исполняет один job.
- Каждый job имеет отдельный временный каталог. Версия ядра — SHA-256 binary,
  вход — JSON в БД; пользовательский job дополнительно ссылается на неизменяемый
  паспорт dataset, а в результате сохраняется provenance.
- Default timeout 300000 ms; heartbeat раз в 2 s. Stale running старше 60 s
  получает failed на следующем проходе работающего worker, не строго через 60 s.
- Отмена не удаляет историю. Worker останавливает дочернюю группу процессов;
  условный финальный update не позволяет затереть cancelled результатом succeeded.
- Ошибка запуска/вычисления/сохранения не превращается в успешный пустой ответ.
  Автоматического retry нет; терминальные статусы не возвращаются в running.
- Manifest v1 содержит команду, дату, пути, размеры и SHA-256; сам manifest
  в свой список не входит. `execution.log` добавляется worker позже и также не
  обязан быть внутри CLI manifest. Полный реестр артефактов — в БД.
- Малые JSON до 128000 bytes могут попасть в result_summary. Журнал ограничен
  1000000 символов JS, текст ошибки — 4000. Это не хранение полных результатов в БД.
- Частичные объекты после failed/cancelled возможны. Для явно подтверждённого
  удаления собственного завершённого job есть отдельная очередь: сначала
  очищается текущий префикс объектов S3, затем удаляются metadata; ошибка
  оставляет запись и повторяется worker. Активный job и отдельный источник с
  зависимыми jobs не удаляются. Полная очистка возможна лишь без активных и
  завершающихся jobs, в порядке от потомков к источникам. Это не общая
  политика retention: сироты вне запроса, S3 versions и backup остаются
  отдельной задачей. Общего atomic commit PostgreSQL+S3 нет.

## 8. Просмотр результатов и ошибки

Обзор получает последние 100 jobs, а история использует отдельный
owner-scoped endpoint с cursor-пагинацией, фильтрами status/kind/дат UTC,
поиском по точному UUID и общим числом совпадений. List возвращает краткую запись,
подробности и signed URL получаются отдельным запросом по UUID. Ссылка действует
900 секунд и является секретом доступа: не пересылать в публичные логи/аналитику.
Выход из аккаунта не отзывает ранее выданную S3-ссылку мгновенно.
Таблица истории запрашивает следующую страницу при приближении к её нижней границе;
фильтры остаются серверными и сохраняются в URL. При сбое доступен ручной повтор
подгрузки без потери уже показанных строк.

Polling истории сейчас 4 s, активного job 2 s; для завершённого результата ссылки
обновляются раз в 600 s. Экран должен различать queued, running и потерю связи:
сбой polling не значит failed расчёта. Показ прогресса в процентах не реализован.
При истёкшем URL запросить новые детали, а не обещать исчезнувший артефакт.
Паспорт метаданных JSON v1 формируется в web из уже разрешённых пользователю
деталей job. Он сохраняет известный вход, provenance, версии и контрольные
суммы, но не `downloadUrl`, `commandLine`, токены или произвольные метрики.

Неавторизованный запрос → 401, чужой/несуществующий UUID → 404. Пользователь может
читать/отменять только свой job. Успех расчёта означает завершение вычислительной
цепочки, но не научную пригодность модели; качество и применимость описываются отдельно.
