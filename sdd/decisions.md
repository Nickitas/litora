# Реестр архитектурных решений

Дата: 25.09.2026. Здесь закреплены базовые решения и границы их применения.
Для нового спорного решения — отдельный ADR с контекстом, вариантами, последствиями,
статусом и ссылкой на заменяемое решение. Старые ADR не переписывать задним числом.

## ADR-001 — Go владеет научной логикой

Статус: принято, реализовано. CLI и будущий Go worker вызывают одни пакеты.
Альтернатива: повторить алгоритмы в API/web. Отклонена из-за расхождения результатов,
двойного тестирования и невозможности воспроизвести научный расчёт одной версией ядра.
Следствие: TypeScript валидирует transport DTO и управляет заданиями, но не вычисляет модель.

## ADR-002 — PostgreSQL одновременно метаданные и первая очередь

Статус: принято, реализовано. Atomic claim `FOR UPDATE SKIP LOCKED`, heartbeat,
терминальные статусы, ограничение одного job на worker-процесс. Redis/broker пока
не добавляем: нагрузка и требования retry/приоритетов не доказали необходимость.
Пересмотр: измеренный bottleneck очереди, SLA задержки, сложный workflow.

## ADR-003 — S3 для больших файлов, PostgreSQL для реестра

Статус: принято, реализовано. Приватные объекты, SHA-256, временные ссылки от API.
Нет общей транзакции двух хранилищ: cleanup/retention — отдельная будущая функция.
Альтернатива BYTEA/Git отклонена из-за размера, backup и границ доступа.

## ADR-004 — Node worker как промежуточный адаптер

Статус: принято, реализовано. Позволяет связать существующий CLI с API без изменения
математики. Отдельный процесс, whitelist, `spawn` без shell, bounded resources.
Переход на Go worker возможен после стабилизации контракта; не переименовывать Node
процесс в «Go worker» в документации до фактической замены.

## ADR-005 — Один источник знаний и SDD

Статус: принято этой документацией. Содержание в `packages/docs/content/`, инженерный
раздел `sdd/`; корневые `sdd/` и `docs/` содержат ссылки, `AGENTS.md` — инструкции.
Альтернатива отдельных docs у каждого приложения отклонена: копии уже приводили
к рассинхронизации; symlink также неудобен для Git и переносимости.

## ADR-006 — Сохранить shadcn radix-nova, тема «Чёрное море»

Статус: Nova уже используется; унификация темы запланирована. Radix, Tailwind 4,
semantic tokens и Lucide сохраняют совместимость существующих компонентов.
Новый UI-kit/миграция Base UI сейчас не даёт обоснованного выигрыша. Дизайн и
контраст описаны в [спецификации](design-system.md), не реализованы этим ADR.

## ADR-007 — Один сервер Compose и внешний S3 для первого пилота

Статус: рекомендуемый путь развёртывания, требует staging-приёмки. PostgreSQL,
API, worker, web и TLS на одном сервере; файлы вне него. Это не HA: падение хоста
останавливает вычисления и API. Kubernetes преждевременен; запас ресурсов и backup
полезнее оркестратора на старте. Изменение на managed PostgreSQL/несколько worker
согласовывается по измерениям и объёму данных.

Community MinIO помечен неподдерживаемым, репозиторий архивирован 25.04.2026:
[официальный репозиторий](https://github.com/minio/minio). Поэтому существующий
`minio:latest` допустим только как унаследованный изолированный dev-стенд, не
production-рекомендация. Для сервера — managed S3 или отдельно проверенное
поддерживаемое S3-совместимое решение; смена локального MinIO — следующая задача.

## ADR-008 — AWS S3 для production-артефактов

Статус: принято как выбор провайдера и региона, развёртывание ещё не проверено.
Пользователь подтвердил AWS S3 в регионе `eu-central-1` (Франкфурт).
Расположение сервера приложения и требования к передаче данных проверить перед
staging. Альтернатива —
самостоятельно размещённое S3-совместимое хранилище — отклонена для первого пилота:
оно добавляет обслуживание дисков, обновлений и резервирования рядом с вычислениями.

Bucket создаётся оператором заранее, остаётся приватным и имеет versioning.
Приложение использует ограниченные права на чтение/запись объектов и HeadBucket,
не получает CreateBucket/DeleteObject. Автосоздание bucket в production-шаблоне
запрещено. Подписанные ссылки действуют ограниченное время; резервное копирование
и восстановление проверяются отдельно на staging. Значения в production env
должны соответствовать выбранному региону `eu-central-1`.

## ADR-009 — Явная доверенная цепочка proxy для auth

Статус: реализация локально, staging-приёмка отдельно. Production `/api/*` идёт
из Caddy непосредственно в API через отдельную edge-сеть. API доверяет только
статическому адресу Caddy /32; nginx остаётся upstream сайта. Локально доверие
выключено. Альтернативы `trust proxy=true`, число hops и доверие всей приватной
сети отклонены: дополнительные пути к API могут позволить подмену клиентского IP.
Настраиваемый список IP/CIDR сохраняет обычный прямой запуск API без proxy.
Новый rate-limit сервис/Redis не нужен: атомарный счётчик остаётся в PostgreSQL.
Лимит 30/min и NAT/fixed-window ограничения сохраняются; ingress/DDoS отдельно.
Подробная приёмка — [AUTH-009–012](features/0002-auth-trusted-proxy.md).

## ADR-010 — Отдельный профиль тяжёлых научных расчётов

Статус: реализовано локально, ресурсная и научная приёмка ещё открыта.
Полные пользовательские контуры, `mesh` и `seabed_*` используют ту же PostgreSQL-очередь, но помечаются профилем
`heavy`; их забирает только отдельный worker с Gmsh и своим бюджетом CPU/RAM,
времени и выходных файлов. API по-прежнему не запускает расчёт в HTTP-запросе.
Научные входы остаются приватными объектами S3 с серверным SHA-256, а в job
передаются лишь UUID и проверенные численные параметры.

Альтернатива повысить лимиты обычного worker отклонена: тогда небольшие задания
соревновались бы с гигабайтными и теряли предсказуемое время ожидания.
Прямой запуск CLI из controller отклонён из-за длительности, отмены и доступа
к файловой системе. Последствия: два профиля деплоя, отдельная ёмкость диска,
необходимость измерить расход ресурсов и поддерживать Gmsh; масштабирование
heavy worker допускается только после проверки нагрузки и квот.
См. [SCI-001–006](features/0027-web-cli-scientific-workflows.md).

## ADR-011 — Повторное использование собственных артефактов без копирования S3

Статус: реализовано локально; сквозная проверка на тестовом S3 открыта.
Поле входа принимает UUID собственного загруженного файла или распознанного
артефакта успешного собственного расчёта. Пара исходного kind и точного пути
артефакта фиксирует его допустимую роль. API и worker независимо проверяют
владельца, статус, bucket, роль и размер; worker повторно вычисляет SHA-256
после скачивания. Подписанный URL, S3-key и путь пользователя в job не входят.

Отдельную копию объекта не создаём: гигабайтная MSH может служить входом
нескольких следующих шагов. Следствие — удаление исходного успешного результата
должно учитывать зависимые задания; сейчас автоматическая сверка удаляет только
частичные файлы failed/cancelled. Пилотный предел — 2 ГиБ на артефакт и 4 ГиБ
на все научные входы задания. Альтернатива скачать и загрузить файл заново
оставалась функциональной, но удваивала трафик и диск и делала веб-цепочку
неудобной; произвольные артефакты запрещены из-за смешения форматов.

## ADR-012 — TanStack Table для отображения истории, cursor остаётся на API

Статус: реализовано локально; ручная UI-приёмка открыта. Для журнала расчётов
используем `@tanstack/react-table` как headless-модель строк и shadcn `Table`
как существующий визуальный слой. Фильтры и порядок остаются серверными:
клиентская сортировка только загруженного фрагмента искажала бы историю.
`IntersectionObserver` запрашивает следующий cursor через `@litora/api-client`;
кнопка ручной подгрузки остаётся при отключённом observer или сетевой ошибке.

Альтернатива оставить карточки с ручной пагинацией не решала задачу быстрого
чтения длинного журнала. Полная миграция web на TanStack Query ради одного
экрана расширяла бы scope и меняла существующий polling. Следствие решения —
новая зависимость только у web, накопление DOM-строк до конца сессии и
необходимость измерить длинные истории до добавления виртуализации. Контракт
API/БД не меняется. Требования и откат: [срез 0031](features/0031-account-infinite-history-table.md).

## ADR-013 — Переносимый паспорт плоской сетки для QA-03

Статус: реализовано локально; сквозная научная и ресурсная приёмка открыта.
Отчёт `mesh-comparison/v1` сохраняет SHA-256 каждой успешно созданной MSH.
`seabed check-full` принимает отчёт после перемещения MSH только при совпадении
контрольной суммы; старый отчёт без неё работает лишь с исходным путём. Так
worker может разместить приватные входы в своём каталоге без правки научного
паспорта. Роль отчёта задана отдельным типом входа; API сверяет владельца и
роль, worker — размер и digest файла после скачивания. Для web ограничение MSH
фиксировано в 256 МиБ, CLI по умолчанию сохраняет старый безлимитный режим.

Альтернатива переписывать `mesh_file` при staging отклонена: это уничтожило бы
сведения об исходном запуске и скрыло несовпадение MSH. Перенос без проверки
digest также отклонён. Следствия: старый отчёт нужно пересоздать для web;
при изменении MSH Go отказывает до расчёта. Предел 256 МиБ не подтверждает
достаточность RAM и диска — они требуют измерения на тестовом полном наборе.
Требования и откат: [срез 0038](features/0038-web-full-black-sea-qa.md).

## ADR-014 — AI-01 как необязательная стадия сравнения ADAPT-03

Статус: реализовано локально; сквозная ресурсная и научная приёмка открыта.
Web включает экспертные карточки в том же `seabed_compare_adaptive`, после
записи принятого отчёта и до общего manifest. Go повторно читает проверенные
входы и MSH из рабочего каталога этого задания; API передаёт только флаг,
подмножество ID уровней и ограниченную строку анонимизации. Закрытый ключ
организатора публикуется как приватный артефакт владельца, но не копируется
в сводные метрики и JSON-паспорт. Новых ролей и публичных URL нет.

Альтернатива отдельного web-задания по старому ADAPT-03 потребовала бы
переноса MSH и переписывания абсолютных путей в отчёте, что скрывало бы
происхождение; она отклонена до переносимого формата научного паспорта.
Автоматическая выдача ключа экспертам отклонена до контракта ролей и
отрицательных owner-тестов. Следствие: AI-01 увеличивает время, RAM и число
файлов одного heavy job; при недостатке двух успешных генераторов выбранного
уровня весь job завершается ошибкой. Отдельный запуск по готовому web-результату,
сбор оценок и AI-02 остаются открытыми. Требования и откат:
[срез 0039](features/0039-web-expert-cards.md).

## ADR-016: перенос AI-02 в отдельное задание по проверенным SHA-256

Статус: реализовано локально; сквозная сверка CLI ↔ web на реальных данных
открыта. Срез [0040](features/0040-web-ai-necessity.md) добавляет
`seabed_assess_ml`: владелец выбирает шесть приватных файлов, worker размещает
их в отдельном каталоге, а Go сверяет ключ AI-01 с отчётом ADAPT-03 и его
тремя исходными файлами по SHA-256. Пять численных порогов ограничивает API;
CLI по-прежнему работает со старыми путями, если новые флаги не переданы.

Альтернатива — переписывать абсолютные пути внутри связанных SHA-256
JSON — отвергнута из-за потери исходных digest и происхождения. Чтение старых
путей worker отвергнуто из-за обхода owner-изоляции. Сбор оценок в ЛК с
экспертными ролями требует отдельной модели прав и отрицательных тестов,
поэтому сейчас TSV заполняют вне сайта. Следствие: пользователь может
воспроизвести расчёт AI-02, но не весь процесс экспертной разметки; для
научной сопоставимости ещё нужна сквозная проверка одинаковых входных SHA-256.
