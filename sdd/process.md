## Как читать утверждения

| Метка | Значение |
| --- | --- |
| Реализовано | Найдено в коде указанного среза; проверку исполнения указываем отдельно |
| Конвенция | Обязательное правило для нового и изменяемого кода; legacy может отличаться |
| План | Функция или миграция ещё не внедрена |
| Оценка | Инженерное предположение, требует замеров или согласования |

При расхождении не выдавайте желаемое за факт: исправьте описание текущего состояния
и заведите отдельную задачу на приведение реализации к конвенции. Решения о новых
технологиях, доступе к данным и удалении принимает владелец проекта.

## Жизненный цикл изменения

1. Проверить ветку, рабочие изменения, AGENTS и связанные спецификации.
2. Создать описание по [шаблону](templates/feature.md) в
   `sdd/features/NNNN-short-name.md` (каталог создаётся с первой
   реальной функцией). Указать проблему, границы, владельца решения и альтернативы.
3. Присвоить требованиям ID вида `CALC-004`, `AUTH-005`, `UI-003`; не переиспользовать
   уже опубликованные ID. Каждое требование связано с наблюдаемой проверкой.
4. Согласовать изменение публичного поведения, модель данных и критерии приёмки.
   Малый багфикс может описывать это в задаче/PR, не требует искусственного RFC.
5. Написать план и задачи: contracts → API/worker/Go → api-client → web → Swagger
   и документация. Миграцию БД и совместимость включать в план до начала реализации.
6. Реализовать маленькими проверяемыми шагами. Не смешивать изменение математики,
   миграцию хранилища и косметический рефакторинг без необходимости.
7. Выполнить проверки из технических конвенций; приложить команды, результат,
   окружение и причины пропуска. Обновить traceability и статус спецификации.
8. Проверить diff, секреты, зависимости, миграции и откат. Коммит/PR/push — только
   в рамках поручения пользователя; в этой задаче коммит делает пользователь.

Статусы спецификации: `draft` → `approved` → `implementing` → `verified` → `released`.
`approved` ставится после согласования владельцем, `verified` — после приёмочных
проверок, `released` — после фактического выпуска. Документация сама эти этапы не заменяет.

Названия тестов и файлов — указатели на доказательства, а не заявление об их
повторном успешном запуске при каждом редактировании этого текста.

## Definition of Done

- Проверяемые требования выполнены; оговорённые исключения явно перечислены.
- Нет второй реализации научной формулы в TS, второго DTO или копии документации.
- Ошибки, таймаут, отмена, пустые данные и запрет чужого доступа покрыты по риску.
- Изменение БД добавлено новой миграцией, описана совместимость и восстановление.
- UI работает с клавиатуры в светлой/тёмной теме и на узком экране.
- Swagger соответствует HTTP, README/SDD описывают реальное поведение.
- Нет секретов, локальных баз, больших расчётных результатов и случайных lockfile diff.
- Для релиза выполнены staging smoke, проверка ресурсов и backup/restore.

## Где менять документы

Полное содержание инженерных спецификаций — только в `sdd/`. `AGENTS.md` служит
коротким операционным входом для инструментов. Описательные и научные материалы
для сайта создаются отдельно в `packages/docs/content/`; не копируйте сюда их
тексты. Никаких symlink и нового `apps/lito-cli/docs`. Изменение поведения может
потребовать обновления обоих наборов документов, каждый для своей аудитории.
