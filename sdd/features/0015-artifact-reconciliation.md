# 0015 — ручная сверка частичных S3-артефактов

- Статус: локальный срез A6; production/staging apply не выполнялся.
- Область: операторская команда API, PostgreSQL, приватный S3 bucket.

## Контракт и границы

`artifacts:reconcile` по умолчанию выполняет только `HEAD` bucket, `LIST`
объектов под `users/` и `SELECT` в БД. Она не вызывает миграции и не создаёт
bucket. Лимит одного полного обхода — 10 000 объектов; при превышении скрипт
завершается без удаления. Отчёт включает число кандидатов и 20 примеров.

Кандидат на удаление должен одновременно удовлетворять условиям:

1. Ключ строго соответствует `users/<job UUID>/<путь результата>` и не является
   входным `datasets/` или диагностическим `failure.log`.
2. Job существует, находится в `failed`/`cancelled` и завершился минимум
   24 часа назад. S3-объект также старше порога и имеет ETag.
3. Если в БД есть запись об объекте, она принадлежит тому же job.

`--apply` — отдельное явное действие оператора, до 100 удалений за запуск.
Перед каждым удалением повторно проверяются статус/возраст job, владелец
metadata и ETag/время объекта через `HeadObject`. Удаление объекта S3
предшествует удалению его metadata. Задания `succeeded`, `queued`, `running`,
неизвестные ключи, импортированные `calculations/` и пользовательские datasets
не трогаются. AWS S3 versioning оставляет старые версии под delete marker;
это не освобождение физического объёма и не retention policy.

Между `HeadObject` и `DeleteObject` остаётся окно гонки: повторная запись по
тому же ключу может быть удалена. Поэтому `--apply` допускается только при
остановленных worker'ах и записи артефактов; следующий срез должен закрепить
условное удаление по версии объекта либо устранить повторное использование ключа.

При сбое между S3 DELETE и SQL DELETE возможна строка metadata без текущего
объекта. Отчёт о таких ссылках добавлен отдельным [срезом 0016](0016-missing-artifact-report.md).
Скрипт не запускается по расписанию. Нужны аудит, стейджинговая проверка прав
и восстановление из backup. Это не закрывает A6.

## Проверка

- Unit: только старые `failed`/`cancelled`; active/succeeded/unknown,
  `failure.log`, datasets и свежие файлы не попадают в план.
- Dry-run на изолированном bucket: нет мутаций; подсчёт и фильтрация.
- `--apply` не запускать на пользовательском хранилище без сверенного отчёта и
  отдельного операторского решения.
