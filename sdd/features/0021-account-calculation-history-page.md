## Проблема и границы

`GET /api/calculations` возвращает только последние 100 собственных jobs.
Экран истории не может показать более старые результаты или достоверно считать
найденные записи. Добавляем отдельный `GET /api/calculations/page` для истории;
старый endpoint остаётся совместимым для обзора и существующих клиентов.
Не добавляем названия jobs, свободный текстовый поиск, удаление или общий доступ.

## Требования и приёмка

| HISTORY-003 | Строгий cursor | Given некорректный cursor или cursor от иных фильтров, When вызван endpoint, Then ответ 400 без SQL-инъекции или раскрытия чужой записи | Unit |

## Контракты и модель данных

`GET /api/calculations/page` принимает необязательные `status`, `kind`,
`from`, `to` (UTC `YYYY-MM-DD`, включая границы), `jobId` (точный UUID),
`limit` (1–50, default 20) и opaque `cursor`. Неизвестные поля, массивы,
невалидные значения и `from > to` → 400. Ключ поиска — только точный UUID,
поскольку пользовательского названия job нет. Ответ:
`{ items: CalculationJobDto[], nextCursor: string | null, totalCount: number }`.
Список не содержит артефактов и summary, как legacy endpoint.

Cursor версии 1 содержит `(createdAt, id)` с точностью PostgreSQL до микросекунд
и отпечаток фильтров (без limit),
кодированный base64url. Он не даёт полномочий: каждый SQL-запрос обязан
ограничивать `user_id`. Это keyset-пагинация по данным в момент запроса,
не зафиксированный снимок БД; новые jobs могут появляться перед первой страницей.
`totalCount` — текущий счётчик по выбранным фильтрам. В URL сохраняются только
фильтры и cursor без токенов, signed URL и персональных входных данных.

Новый индекс `(user_id, created_at DESC, id DESC)` добавляется отдельной
миграцией 008. Он не меняет существующие строки или старый API. Откат кода
совместим с индексом; удаление индекса, если нужно, — отдельная миграция.
Текущий транзакционный runner не поддерживает `CREATE INDEX CONCURRENTLY`:
на большой таблице индекс может временно блокировать запись. Перед production
нужны замер на staging и подходящее окно обновления.

## Риски и альтернативы

- Offset пропускает/дублирует записи при новых jobs; выбран keyset и UUID tie-breaker.
- Cursor не подписан, но строго валидируется и привязан к фильтрам; даже
  подделанный cursor не снимает owner-фильтр. Он не содержит секретов.
- Свободный текстовый поиск не вводится без поля/индекса и согласованной семантики.
- Подсчёт по фильтру требует дополнительного SQL-запроса; для пилота это
  честнее, чем счётчик только текущей страницы. Нагрузку измерить до расширения.
- Ручная проверка обеих тем, 360 px и 200% zoom остаётся условием verified.
