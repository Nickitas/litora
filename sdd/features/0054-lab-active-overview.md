## Проблема и границы

Обзор `/lab` берёт только последние 100 расчётов и оставляет три активных.
Старый `queued` может исчезнуть после множества завершённых jobs; четвёртый и
пятый активные не показываются. После неудачной первой загрузки пустой массив
ошибочно сопровождается текстом «Нет активных расчётов». Исправляем обзор,
сохраняя историю и существующие права доступа. Новые endpoint, DTO, миграции,
научные методы и квоты не вводятся.

## Контракты и модель данных

Web вызывает существующий `GET /api/calculations/page` отдельно для `queued` и
`running` с `limit=50`; API фильтрует оба запроса по `user_id`. `totalCount`
позволяет не скрывать возможное усечение. Для недавних остаётся существующий
`GET /api/calculations` с лимитом 100. При переходе статуса между двумя
запросами одинаковый UUID показывается один раз; следующий polling обновляет
снимок. API-ready не свидетельствует о доступности worker.

## Риски и альтернативы

Два снимка статусов не являются одной транзакцией, поэтому при переходе
`queued → running` кратковременная несовместимость возможна. Отдельный API
агрегат устранил бы её, но потребовал бы новый контракт и больше кода без
текущей потребности. Нельзя брать `activeCount` из удаления вместо списка:
он сообщает число, но не даёт карточек. Ошибка одного запроса не должна
заменять известный полный снимок частичным.
