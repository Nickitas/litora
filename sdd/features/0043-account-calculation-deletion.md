# 0043 — удаление расчётов из личного кабинета

- Статус: реализовано локально; проверка на изолированном PostgreSQL/S3 и production IAM открыта.
- Владелец решения: команда Litora; правило подтверждено пользователем 14.10.2026.
- Исходный SHA: `34ffdf6`; связанные ADR: 003, 008, 011, 019.
- Область: contracts, API, PostgreSQL, worker, api-client, web.

## Проблема и границы

Владелец может запросить удаление одного завершённого расчёта либо всей собственной
истории. Активные jobs не удаляются. Источник с зависимым расчётом нельзя удалить
отдельно; полная очистка принимает только набор без активных/завершающихся jobs
и идёт от потомков к источникам. Фильтры таблицы не влияют на полную очистку.
Загруженные `datasets` и `scientific_inputs` вне операции.

«Безвозвратно» означает отсутствие отмены и восстановления через ЛК. В versioned
S3 `DeleteObject` скрывает текущую версию, но noncurrent versions и backup
сохраняются до отдельной операторской политики. Мгновенное уничтожение всех
физических копий и удаление аккаунта здесь не реализуются.

## Контракты и модель данных

- `GET /api/calculations/deletion-overview`: число своих jobs по состояниям.
- `DELETE /api/calculations/:id` и `DELETE /api/calculations`: `202` и
  `CalculationDeletionRequestDto`; `404` для чужого/отсутствующего job,
  `409` для активного, завершающегося, зависимого или уже удаляемого.
- `GET /api/calculations/deletions/:requestId`: только собственная операция.
- `GET /api/calculations/deletions-current`: последняя незавершённая операция
  владельца для восстановления прогресса после обновления страницы.
- Миграция `014`: `deletion_requested_at`, связи источника и потомка с backfill
  по UUID научных входов, durable queue и аудит удаления.
- Новые ссылки на артефакты создаются под user-row lock; тот же lock используется
  для запроса удаления. Ссылка на помеченный источник запрещена.
- Worker очищает текущие S3-объекты под проверенным job-prefix. При ошибке
  оставляет job и повторяет с ограниченным backoff. После успеха в одной
  PostgreSQL-транзакции удаляет job, события, артефакты, рёбра зависимостей и
  завершает item. Повтор после падения идемпотентен на уровне доступа к объекту.
- Массовый запрос — снимок всех своих jobs на момент подтверждения; новые jobs
  позже в него не попадают. Запрос без jobs сразу завершён.

## Риски и альтернативы

Синхронное удаление в HTTP отвергнуто: тысячи файлов, timeout и разрыв между
S3/PostgreSQL. Soft delete без очистки файлов не отвечает задаче.
`DeleteObjectVersion` приложению не выдаётся: оно уничтожило бы историю
versioned bucket. Для production worker нужно `DeleteObject`; без права операция
останется в повторе, но строка БД не потеряется. Лог не содержит ключей S3,
signed URL и входных параметров. Повреждённый ключ требует оператора.
