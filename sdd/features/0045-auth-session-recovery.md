# 0045 — бесшовное восстановление web-сессии

- Статус: реализовано локально; проверка в staging и других браузерах открыта.
- Дата: 15.10.2026; исходный SHA: `fbb6b35`.
- Область: `packages/api-client`, `apps/lito-web`; API, DTO и БД не меняются.

## Проблема и границы

API ротирует refresh-cookie и access-token при каждом refresh. Прежний web-клиент
делил только одновременно выполняющийся refresh одной вкладки. Поздний 401
запроса со старым access-token запускал новую ротацию; две вкладки могли отправить
старую cookie одновременно, после чего проигравшая показывала «Сессия истекла».
Перезагрузка использовала уже обновлённую cookie и восстанавливала вход. При
сетевой ошибке начальной проверки web также ошибочно переводил пользователя на вход.

Срок сессии 30 дней от создания и серверная одноразовость refresh остаются
неизменными. Не храним токены в persistent storage, не меняем лимиты API и не
продлеваем сессию бессрочно.

## Требования и приёмка

| ID | Требование | Given / When / Then | Доказательство |
| --- | --- | --- | --- |
| AUTH-REC-001 | Поздний 401 | Два защищённых запроса ушли со старым access-token; первый обновил сессию, второй ответил позже → второй повторяется с новым токеном без новой ротации и предупреждения | E2E |
| AUTH-REC-002 | Две вкладки | Одновременное открытие с одной refresh-cookie → обе вкладки остаются в кабинете | E2E Chromium |
| AUTH-REC-003 | Временный сбой | Начальный refresh получил 503/сетевую ошибку → вход не объявляется завершённым, доступна повторная проверка | E2E |
| AUTH-REC-004 | Подтверждённое окончание | У активного пользователя refresh дважды получил 401 после повторной проверки → переход на вход с понятным сообщением | E2E |
| AUTH-REC-005 | Безопасность | Токены только в памяти вкладок; logout отзывает серверную сессию; чужие данные не переживают смену пользователя | Код и ручная проверка |
| AUTH-REC-006 | Выход из двух вкладок | Logout в одной вкладке → обе переходят на вход без ложного сообщения об истечении | E2E Chromium |

## Контракты и модель данных

`AuthDto`, HTTP-статусы, cookie и схема PostgreSQL не изменяются. Клиент
запоминает срок access-token только в памяти, обновляет его незадолго до
истечения и повторяет защищённый запрос после подтверждённого обновления.
`401` защищённого endpoint сам по себе не равен завершению сессии; решает
результат `/auth/refresh`. `429`, `503` и ошибка сети не очищают авторизацию.

Для вкладок одного origin используется `Web Locks` на refresh/logout и
`BroadcastChannel` для передачи текущего access-token в память открытых
вкладок. При отсутствии этих API остаются одно-вкладочный single-flight и
ограниченный повтор после гонки. Local/sessionStorage токенов нет. При смене
пользователя дерево маршрутов перемонтируется, чтобы не оставить данные старого
аккаунта в состоянии компонентов.

## Риски и альтернативы

Серверный grace-период старой refresh-cookie отклонён: он ослабил бы
одноразовость токена и потребовал бы хранить/восстанавливать следующее значение.
Отказ от ротации также противоречит текущему контракту. Нативные браузерные
API не добавляют dependency, но fallback в старых браузерах и вкладки со старой
версией приложения требуют отдельной ручной проверки. Сообщение между вкладками
доступно только тому же origin; токен не записывается на диск приложением.
См. ADR-020.
