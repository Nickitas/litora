# 0056 — приёмка heavy-пути закрытого пилота

- Статус: техническая цепочка до `compare` проверена локально; `validate`,
  ресурсные лимиты и научная приёмка открыты.
- Дата: 19.10.2026; локальный HEAD `151d08b` плюс незакоммиченный diff.
- Владелец решения: команда Litora.
- Область: Go CLI, Gmsh, heavy worker, API, PostgreSQL, приватный S3.
- Решение владельца от 19.10.2026: heavy обязателен в ближайшем закрытом
  пилоте. Отсутствие готовых входов откладывает приёмку пилота, а не исключает
  heavy из его состава. Точный список открываемых пользователю heavy-kind
  будет закреплён отдельно.

## Проблема и границы

Каталог предлагает `mesh` и сценарии seabed только при включённом heavy-профиле.
Наличие команд и Gmsh не доказывает, что полный расчёт дна помещается в ресурсы
стенда или что исходные данные пригодны для научного вывода. Этот протокол
отделяет технический smoke малого входа от приёмки цепочки на лицензированных
научных данных. Права доступа, DTO и алгоритмы этим срезом не меняются.

## Локальный технический прогон HEAVY-01

- Вход: `apps/lito-cli/data/examples/sochi-local-segment.geojson`, SHA-256
  `5fc2e8625fc57021fb760cccc63cb6ff20848edd70e159453f34402faa99129a`;
  OpenStreetMap way 59530506, выгрузка 17.08.2026, ODbL. Это стартовый
  сегмент, не полный контур Чёрного моря и не инженерная съёмка.
- Параметры: `cellSizes=2000`, `boundaryDetails=2000`,
  `generators=frontal-quad`, `maxCells=1000`, timeout Gmsh 1 минута.
  Go `1.25.4 darwin/arm64`, Gmsh `4.15.2-git`, Node `22.12.0`.
- Standalone CLI: `go build -trimpath`, затем `lito mesh` с `--manifest` и
  указанными параметрами. MSH содержит 15 четырёхугольных ячеек;
  SHA-256 `d438b6e929cf5717b13d9e8638181149e99e320e4f395c7ad86521be564b5bdb`.
  Повтор дал тот же SHA. Локальное `/usr/bin/time -l`: 0,30 с real,
  maximum resident set size 29 458 432 байта **для процесса CLI**; пик
  дочернего Gmsh отдельно не измерен. Каталог результата: 7 файлов, 28 КиБ
  выделенного места на APFS. Это не оценка peak scratch для полного задания.
- HTTP: `TEST_HEAVY_ENABLED=true TEST_MESH_ENABLED=true
  TEST_MESH_CLI_BINARY=/private/tmp/litora-heavy-acceptance-cli pnpm test:integration`
  на отдельной PostgreSQL 17 и локальном MinIO с tmpfs, портами только
  `127.0.0.1`. API, standard и heavy worker запущены из исходников через
  `tsx`, Go CLI собран локально. Job `succeeded`, профиль `heavy`, 0,454 с
  между `started_at` и `finished_at`, 8 опубликованных файлов. MSH имеет тот
  же SHA-256 и размер 2557 байт. Тест проверил SHA-256 скачанных MSH,
  отчёта и manifest v2, подпись 900 с, отказ для URL без подписи и 404
  для чужого UUID. Тест дополнительно запустил тот же CLI на том же файле и
  сравнил SHA-256 MSH с worker. Общий integration-прогон завершился успешно; его
  standard- и dependent-сценарии также прошли.
- Изолированные контейнеры остановлены с `--rm`; одноразовые БД и объекты
  были в tmpfs. Файл приглашений и журнал теста удалены из `/private/tmp`.
  Данные и подписи не включены в протокол.

### Проверка целевого Docker-образа 19.10.2026

- Исходный heavy-образ с Debian Bookworm Gmsh 4.8.4 на `linux/arm64`
  завершался ошибкой `Unknown number option 'Mesh.Reproducible'` и
  segmentation fault на том же `.geo`. Поэтому он не годился для пилота.
- Новый heavy Dockerfile использует официальный headless Gmsh `4.15.2-nox`
  для `linux/amd64`, SHA-256 архива
  `2f81d19efb0dd94426bdab010131da59b7dac1939a3073890dc32c86ecbaa8db`.
  Сборка `docker build --platform linux/amd64 --target heavy` и проверка
  `gmsh --version` прошли. Локальный image ID не является GHCR release digest.
- Отдельный Go CLI внутри этого образа на том же сегменте и параметрах создал
  15 четырёхугольных ячеек; SHA-256 MSH
  `1a7978a4cd24eae2a57e4c04a5512db535d0ead1d98da709eb24270f5b49f06d`.
  Отличие от macOS Gmsh `4.15.2-git` допустимо для этого технического smoke:
  сравнение выполняется между CLI и worker **на одном образе и версии Gmsh**.
- API, standard worker и отдельный `linux/amd64` heavy worker запущены из
  собранных образов на одноразовых PostgreSQL 17 и приватном MinIO с tmpfs.
  `TEST_HEAVY_ENABLED=true TEST_MESH_ENABLED=true
  TEST_MESH_REFERENCE_SHA256=1a7978a4cd24eae2a57e4c04a5512db535d0ead1d98da709eb24270f5b49f06d
  pnpm test:integration` прошёл: 8 артефактов mesh, тот же SHA-256 MSH,
  manifest v2, контрольные суммы скачанных файлов, signed URL, 403 без подписи
  и 404 для другого пользователя. Также прошли standard и dependent-сценарии.
  Это локальный сквозной тест контейнеров; staging и ресурсный профиль полного
  расчёта пока не проверены.
- После прогона операторский запрос `queue-status --profile heavy
  --require-worker --json` показал `recentWorkerCount=1`, пустую очередь и
  `no_alerts`. `scratch-cleanup.js` без `--apply` просмотрел 0 каталогов,
  удалил 0. Это подтверждает только dry-run после штатного малого задания;
  восстановление volume и OOM под полной нагрузкой остаются открытыми.

### Техническая цепочка с GEBCO_2026 19.10.2026

- Из указанного в `black-sea-bathymetry-source.json` официального OPeNDAP
  получен срез 40,5–47,5° с. ш., 27–42,5° в. д. Сетка 1680×3720,
  диапазон elevation −2666…5560 м совпал с описанием выбранного источника.
  Файл NetCDF содержит 12 569 007 байт; SHA-256
  `53303c17934c7a30a59bc440dc82c1870f527ba7535212a2fca9158b808dbc6d`.
  Это **новая сериализация** xarray 2026.9.0/netCDF4 1.7.5, а не восстановление
  байт прежнего файла: его SHA в двух документах указан по-разному.
  Добавлен `fetch_gebco_region.py` с фиксированным URL, границами и проверкой
  1680×3720; повторная выгрузка тем же окружением дала тот же SHA-256.
- Существующий конвертер с шагом 0,02° сохранил 134 161 подводную точку,
  SHA-256 JSON `c6835d4a420f4c253b27b0784e12a92fe7c3d25393d27b3bac03a8a8d505795d`.
  Паспорт фиксирует исходный URL, SHA-256 NetCDF, шаг, метод nearest,
  знак отметок, допущение среднего уровня моря и ограничения GEBCO. Копия
  NetCDF, JSON и паспорта лежит только в игнорируемом Git каталоге
  `apps/lito-cli/output/acceptance/heavy-2026-10-19/`; оба SHA проверены.
  Этот кандидат не объявлен утверждённым входом пилота.
- В одном `linux/amd64` heavy-образе малый Sochi `mesh → seabed build →
  render → adapt → generate-adaptive → compare-adaptive` завершился. `build`
  дал покрытие 100% для 23 узлов и 15 ячеек; SHA-256 MSH модели дна
  `706990b6b45940cf1a987fbc9843d3e83d6d6cc277e9d50deff067893e037ffa`.
  `compare-adaptive` принял локальный уровень: 3 успешных генератора, 0 ошибок.
  Это проверка исполнения на коротком сегменте, не независимая оценка точности.
- Отдельный `pnpm test:integration` с `TEST_SEABED_BATHY_JSON`,
  `TEST_SEABED_BATHY_METADATA`, `TEST_SEABED_REFERENCE_SHA256` и
  `TEST_SEABED_CHAIN_ENABLED=true` передал производный набор и паспорт через
  API, использовал приватный артефакт предыдущего `mesh` и выполнил
  `seabed_build → seabed_render → seabed_adapt →
  seabed_generate_adaptive → seabed_compare_adaptive` в heavy worker.
  Опубликовано соответственно 13, 8, 5, 8 и 22 файла; SHA-256 MSH совпал с
  CLI, скачанные результаты и manifest v2 проверены, прямые URL без подписи
  дали 403, чужие UUID — 404. Интеграционный тест подтвердил прохождение
  jobs и приватную доставку; отдельный CLI report `compare` содержал
  `accepted=true`. Это не проверка независимого `validate`.

### Локальные отказы heavy worker 19.10.2026

- Для воспроизводимого долгого выполнения только в одноразовом контейнере
  системный `gmsh` был заменён тестовым процессом ожидания. При
  `JOB_TIMEOUT_MS=3000` job завершился `failed`: опубликован только
  `failure.log`, MSH отсутствует. При отмене до истечения длинного timeout
  статус стал `cancelled`, артефактов не осталось.
- Во время другого запущенного mesh тестовый worker был принудительно
  остановлен. В одноразовой PostgreSQL heartbeat этого job переведён за
  порог stale; новый штатный heavy worker отметил job как `failed` с
  причиной потери связи и без опубликованных артефактов. Следующий mesh на
  этом worker завершился `succeeded` с тем же SHA-256 MSH
  `1a7978a4cd24eae2a57e4c04a5512db535d0ead1d98da709eb24270f5b49f06d`.
  Операторский `queue-status --profile heavy --require-worker --json` после
  проверки: `no_alerts`, `queuedCount=0`, `runningCount=0`,
  `recentWorkerCount=1`, `failed24hCount=2` (ожидаемые timeout и crash).
  Проверка не моделирует перезапуск PostgreSQL/S3, потерю volume или OOM.

Дополнительно standalone `mesh` на встроенном грубом `data/black-sea.json`
с ребром 200 км и детализацией 20 км создал 48 ячеек за 0,28 с. Вход
схематичен, разрешение предельно грубое, поэтому этот запуск не задаёт
лимиты production и не считается приёмкой полного контура.

## Следующий проверяемый шаг

Проверить и согласовать подготовленный региональный кандидат GEBCO с учётом
маски акватории, TID, вертикального датума и применимости выбранного полигона.
Перед использованием в пилоте сверить исходный NetCDF: для одного имени файла
`black-sea-bathymetry-source.json` и
`black-sea-bathymetry-source.metadata.json` сейчас содержат разные SHA-256,
или объявить прежний паспорт воспроизведённым; новый кандидат имеет собственный
SHA-256 и сохранённый исходник только в локальном `output/`.
Закрепить независимую опорную модель для `validate` и численные допуски до
научной приёмки. Затем выполнить оставшуюся часть HEAVY-02–04 на выделенном стенде с измерением
всего дерева процессов, scratch и ограничений результата. До этого пилот с heavy не объявлять принятым
и не открывать непроверенные сценарии пилотной аудитории.

Проверки этого среза: `node --check scripts/integration-test.mjs`,
изолированный `pnpm test:integration` с mesh и всей opt-in seabed-цепочкой,
локальные пробы timeout/cancel/crash/restart, `pnpm verify`,
`pnpm check:workspace`, `git diff HEAD --check` и сборка целевого heavy-образа.
Staging, реальные S3/IAM, backup/restore и браузер здесь не проверялись.
