## Проблема и границы

Каталог сохраняет фиксированное название без возможности изменить его.
Загрузка файла позволяет редактирование, но одинаковые имена файлов дают
одинаковые предложения. Распознавание сохранённого примера сейчас включает имя,
поэтому его изменение ошибочно воспринималось бы как новый контур.

Добавляем редактируемое поле в карточку примера и единое правило предложения
свободного названия. Для каталога указываем место и известную версию OSM либо
дату выгрузки; дата выгрузки явно обозначена и не выдаётся за дату съёмки.
Для файла используем имя без расширения `.geojson`/`.json`.
Переименование уже сохранённых записей и подготовка новых научных данных
не входят в эту задачу.

## Контракты и модель данных

DTO, runtime-валидация API, Swagger, owner-проверки, checksum геометрии, БД и
миграции сохраняются. Пользовательский `name` уже отделён от паспорта в контракте.
Предложение — удобство формы по загруженному списку, а не гарантия уникальности
в БД или между вкладками. Пользователь может намеренно ввести совпадающее имя;
источником идентичности остаются ID и паспорт, а не название.

`findSavedExample` продолжает сравнивать checksum, source/sourceRevision,
license, CRS, единицы и число точек; имя исключается из сравнения. Поэтому форма
расчёта также повторно использует переименованный пример без новой записи.
В метаданные каталога добавляется отдельное предложение имени, без изменения
исходных DTO/геометрии и контрольных сумм.

## Риски и альтернативы

- Жёсткая уникальность потребовала бы контракта и миграции, хотя совпадение имён
  допустимо сегодня. Ограничиваемся предложением; существующие записи не меняем.
- Выделять версию из произвольного текста источника ненадёжно. Для трёх учебных
  карточек задаём явное предложение по уже известным метаданным.
- Отдельный диалог добавил бы действие перед сохранением. Поле находится прямо
  в карточке с существующей кнопкой; состояние загрузки/ошибки сохраняется.
- Идентичная геометрия с другой версией/источником остаётся отдельным набором.
