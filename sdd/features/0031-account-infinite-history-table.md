## Проблема и границы

История уже запрашивает owner-scoped страницы по cursor, но показывает их как
отдельные карточки с ручным переходом. Для просмотра длинного журнала нужна
компактная таблица, которая накапливает строки при прокрутке. TanStack Table
отвечает только за модель строк и ячеек; фильтрация и порядок остаются на API.
Новых способов сортировки, поиска по названию или доступа к чужим jobs нет.

## Требования и приёмка

| ID | Требование | Given / When / Then | Доказательство |
| --- | --- | --- | --- |
| HISTORY-TABLE-001 | Читаемый журнал | Given расчёты разных статусов, When открыт раздел, Then таблица показывает сценарий, статус, время и действия; полные данные остаются на detail | E2E, visual |
| HISTORY-TABLE-002 | Серверные фильтры | Given статус, сценарий, UTC-период и точный UUID, When изменён фильтр, Then URL и API-параметры обновляются, накопленные строки очищаются, чужая страница не попадает в новый список | E2E |
| HISTORY-TABLE-003 | Бесконечная подгрузка | Given `nextCursor`, When нижняя граница таблицы приближается к viewport, Then следующая страница запрашивается один раз, строки добавляются без дублей; после `null` запросов больше нет | E2E |
| HISTORY-TABLE-004 | Состояния и доступность | Given загрузка, ошибка и конец истории, When меняется состояние, Then есть skeleton, отдельная ошибка первой/следующей страницы, кнопка ручной подгрузки, счётчик и объявления для screen reader | E2E, visual |
| HISTORY-TABLE-005 | Адаптивность | Given 360 px, две темы и клавиатура, When пользователь работает с таблицей, Then статус и действия доступны через осмысленную горизонтальную прокрутку, фокус видим | E2E, ручная проверка |

## Контракты и модель данных

Используется текущий `GET /api/calculations/page` с `status`, `kind`, `from`,
`to`, `jobId`, `limit`, `cursor`. Порядок остаётся `(created_at DESC, id DESC)`.
Первый запрос и периодическое обновление первой страницы используют существующий
polling 4 s; уже просмотренные строки не исчезают при появлении новых jobs.
Повторяющиеся UUID при сдвиге границы страницы объединяются. Изменение фильтра
сбрасывает накопление. Старые ссылки с `cursor` открывают соответствующую
страницу и позволяют вернуться к началу; новая подгрузка не раздувает URL
opaque cursors. Signed URL не попадают в таблицу или адресную строку.

## Риски и альтернативы

- `IntersectionObserver` может сработать повторно: запрос следующего cursor
  блокируется на время выполнения, а при ошибке остаётся явная кнопка повтора.
- Polling первой страницы не даёт snapshot БД; новые jobs вставляются в начало,
  ранее загруженные сохраняются. Это не обещание абсолютной консистентности
  длинного журнала при одновременных изменениях.
- Клиентская сортировка только загруженных строк вводила бы в заблуждение.
  Заголовки не сортируются до поддержки серверного порядка.
- TanStack Query потребовал бы отдельной миграции состояния всего web.
  Здесь добавляется только запрошенный `@tanstack/react-table` и небольшой hook
  вокруг существующего API client.
- Строки накапливаются без виртуализации. Для очень длинной сессии потребуется
  замер DOM/памяти и, при подтверждённой проблеме, отдельная виртуализация.

## Проверки и выпуск

Новая зависимость локальна web; миграций БД и изменения API нет. При откате
возвращается прежнее отображение карточек и ручная кнопка следующей страницы.
09.10.2026: `pnpm verify` прошёл (typecheck, lint, web/API/CLI tests и сборки,
bundle gate). Первый sandbox-прогон остановился на API-тесте, открывающем
`127.0.0.1`; повтор в окружении с разрешённым локальным портом прошёл.
`pnpm --filter litora-web test:e2e` — 32 пройдено, один live-сценарий пропущен
без отдельного окружения. E2E проверяют скролл, отсутствие дублей, URL-фильтры,
ошибку и повтор подгрузки, сравнение между страницами, 360 px и клавиатуру.
Снимки таблицы просмотрены в светлой desktop и тёмной мобильной темах;
обнаруженное сжатие поля UUID на мобильном исправлено и проверено E2E.
Интеграционный тест с PostgreSQL/MinIO и ручная screen-reader/zoom приёмка
не запускались. Новых секретов, миграций и downtime нет.
