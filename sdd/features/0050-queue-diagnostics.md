# 0050 — диагностика очереди расчётов для оператора

- Статус: реализовано и проверено локально; приёмка staging открыта.
- Дата: 18.10.2026; исходный SHA `756610b`, ветка `development`.
- Владелец решения: команда Litora.
- Область: служебная команда API, PostgreSQL SELECT, документация; A5/D3 плана.

## Проблема и границы

`/api/health` проверяет БД и S3, но не исполнение очереди. При остановленном
worker пользовательские задания могут ждать бесконечно, а старый `running`
получит `failed` только после прохода другого работающего worker. Оператору
нужен ограниченный снимок двух очередей без чтения входных файлов и персональных
данных.

Добавляем `pnpm --filter litora-api queue:status` и соответствующий compiled
entrypoint для контейнера. Команда только читает пользовательские `queued` и
`running` jobs. Она не меняет статусы, не повторяет задания, не применяет
миграции и не обращается к S3. Пустая очередь не подтверждает живой idle worker:
реестр heartbeat самого процесса и доставка алертов остаются следующим срезом.
Очередь удаления и импортированные jobs без владельца в этот снимок не входят.

## Требования и приёмка

| ID | Требование | Given / When / Then | Доказательство |
| --- | --- | --- | --- |
| QUEUE-DIAG-001 | Раздельный снимок профилей | Given standard/heavy и завершённые jobs, When вызвана команда, Then по каждому профилю видны только собственные счётчики активных пользовательских jobs, возраст самого старого ожидания и heartbeat | PostgreSQL-тест с временной таблицей |
| QUEUE-DIAG-002 | Потерянный heartbeat | Given running с worker и heartbeat старше 60 с либо без heartbeat, When построен снимок, Then есть сигнал `stale_running`; running без worker даёт отдельный `unassigned_running` | Граничные PostgreSQL-тесты |
| QUEUE-DIAG-003 | Длительное ожидание | Given queued старше настраиваемого порога (default 300 с), When построен снимок, Then есть предупреждение `queue_wait_exceeded`, но нет утверждения о смерти worker | Тест порога и профилей |
| QUEUE-DIAG-004 | Машинный и человекочитаемый вывод | Given `--json` или обычный вызов, Then возвращается JSON v1 либо русский текст; exit 0 — сигналов нет, 1 — требуется внимание, 2 — неверные параметры/ошибка проверки | Unit/CLI smoke |
| QUEUE-DIAG-005 | Безопасная эксплуатация | Given ошибка подключения, пустая очередь или неизвестная опция, Then нет секретов/UUID/входов/stacktrace; неизвестное состояние worker явно обозначено, SQL ограничен SELECT и одним снимком времени БД | Тесты и read-only smoke |

## Контракты и модель данных

Публичные DTO, endpoint, Swagger, web, схема БД и права не меняются. Используются
существующие `resource_profile`, `created_at`, `worker_id`, `heartbeat_at`,
`status`, `user_id`. SQL агрегирует данные на сервере, не выгружая всю историю.
JSON v1 содержит `observedAt`, `status` (`no_alerts`/`attention`), `profiles` и
`alerts`. Профиль включает queued/running, stale/unassigned running и возрасты
в секундах. `workerAvailability=unknown` явно ограничивает смысл результата.

`--profile=all|standard|heavy`, `--queue-wait-seconds=1..604800`,
`--stale-after-seconds=60..86400`, `--json`, `--help`. Изменение порога проверки
не меняет 60-секундную логику восстановления в worker. Время берётся из БД,
поэтому часы запускающего компьютера не меняют оценку heartbeat. Новых env нет:
используется штатная конфигурация API, включая `LITORA_ENV_FILE`.

## Риски и альтернативы

- Длительная очередь может быть нормальна для тяжёлой задачи. Предупреждение
  означает превышение операторского порога, не неисправность; порог выбирают
  по измеренному времени обслуживания.
- Без heartbeat idle-процесса нельзя доказать его доступность. Последующий
  срез должен добавить ограниченный реестр worker и проверку возможностей
  профиля; это не повод подменять проверку контрольного job пустой очередью.
- Операторская команда видит агрегаты всех владельцев через существующий доступ
  к БД; публичного admin API не появляется. Ошибки драйвера не печатаются.
- Один агрегирующий SELECT ограничивает передачу данных; на большой активной
  очереди нужен замер плана запроса. Автозапуск, внешний мониторинг и новые
  сервисы в этот срез не входят.

## Проверки и выпуск

Следующее аддитивное изменение [0053](0053-worker-presence.md) повысило
операторский JSON до v2: добавлены свежий heartbeat процесса и число failed
jobs за 24 ч. Описание v1 выше оставлено как исторический срез 0050, не как
текущий формат команды.

Миграций, новых зависимостей и изменения научных методов нет. Откат — убрать
entrypoint; данные не изменяются. PostgreSQL-проверка создаёт только временную
таблицу внутри транзакции в выделенной `litora_test_*`, затем выполняет rollback.
На production интеграционные тесты не запускаются.

18.10.2026: пять целевых проверок пройдены без пропусков, включая PostgreSQL 17
в отдельном контейнере с tmpfs. Проверены ровно 60/61 с heartbeat, null heartbeat,
running без worker, 300/301 с ожидания, пустые профили, будущая дата heartbeat,
исключение завершённых и безвладельческих jobs, ограничение профиля, справка и
отсутствие реквизитов в ошибке CLI.

Общий прогон API с TEST_DATABASE_URL обнаружил две старые неисправности тестов:
HTTP-модуль сессий не предоставлял CalculationDeletionService новому контроллеру,
а тест dataset жёстко ожидал устаревшую версию input schema 3. В тестовом модуле
добавлен сервис и отключён abortOnError, чтобы следующая ошибка DI сообщалась
тестом; ожидание версии связано с текущей константой. Поведение auth/jobs не
менялось. Повторный API-прогон: 96/96, без пропущенных DB-тестов.

Общий `pnpm verify` с TEST_DATABASE_URL этого изолированного контейнера прошёл:
typecheck, lint, web/API/Go-тесты, обе сборки и bundle gate. Остались прежние
предупреждения React Compiler и размера чанка web. Compiled entrypoint
`node dist/scripts/queue-status.js --json` проверен на двух искусственных jobs:
ожидание standard → exit 1, тот же job при увеличенном пороге → exit 0,
устаревший heartbeat heavy → exit 1. После запросов оба статуса сохранились.
Не запускались полный `pnpm test:integration` с S3/worker и staging-smoke:
данный срез не меняет исполнение jobs и проверен на отдельной PostgreSQL,
а полного тестового окружения для серверной цепочки здесь не поднимали.
После приёмки созданный PostgreSQL-контейнер остановлен и автоматически удалён;
его искусственные данные хранились только в tmpfs, пользовательские volumes
не использовались.
