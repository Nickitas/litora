# 0040 — Оценка необходимости ML из кабинета

- Статус: реализовано локально; сквозная проверка на staging открыта.
- Владелец: Litora; дата: 13.10.2026; ветка `development`.
- Область: contracts, Go CLI, API/worker, web, документация; без миграции БД и новых прав.

## Проблема и границы

`seabed assess-ml` уже вычисляет AI-02 по заполненным оценкам AI-01, закрытому
ключу и принятому ADAPT-03. В ЛК команда недоступна. Ключ и отчёт содержат
пути прежнего рабочего каталога, поэтому повторная задача не должна доверять
этим путям, переписывать исходные JSON или обращаться к чужому каталогу.

Новый сценарий `seabed_assess_ml` принимает шесть приватных UUID: TSV оценок,
ключ организатора, отчёт ADAPT-03 и три исходных файла, SHA-256 которых записаны
в отчёте (модель MSH, паспорт EXPORT-02, берег GeoJSON). Go получает только
пути, подготовленные worker, и сверяет ключ ↔ отчёт ↔ исходные файлы по SHA-256.
Роли эксперта, совместное редактирование и сбор оценок на сайте не входят в срез:
владелец собирает заполненный TSV вне ЛК и загружает его как приватный вход.

## Контракты и совместимость

Новый kind и три роли научных файлов: `adaptive_comparison_report_json`,
`expert_organizer_key_json`, `expert_ratings_tsv`. Для TSV/JSON лимит 2 МиБ,
CRS и координатные единицы `not-applicable`. Модель, паспорт и контур используют
существующие роли. Опубликованные артефакты AI-01 и ADAPT-03 становятся входами
только своего владельца. Версия схемы входа 12; worker сохраняет поддержку 1–11.
Результаты помещаются в `seabed/ai-necessity/` и обычный manifest; новых таблиц нет.

CLI получает необязательные флаги путей для переносимого запуска AI-02.
Без них прежний standalone-CLI сохраняет поведение. Переданные worker пути
проверяются против SHA-256 исходного отчёта, а не подменяют его содержание.

## Риски и альтернативы

Переписывать пути и пересохранять ключ/отчёт отвергнуто: это ломает их digest и
происхождение. Автоматически разрешать пути из ключа в новом job отвергнуто:
это обходило бы owner-изоляцию и sandbox worker. Отдельные роли экспертов
требуют нового контракта прав и отрицательных тестов, поэтому не вводятся.
Неполная/ошибочная разметка может дать научный отказ без рекомендации ML; это
не ошибка транспорта. На staging нужна сверка результатов CLI ↔ web по одним
SHA-256, включая отсутствие утечки закрытого ключа в сводку.
