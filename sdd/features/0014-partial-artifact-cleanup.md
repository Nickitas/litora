# 0014 — уборка частичных результатов расчёта

- Статус: локальный срез A6; staging и восстановление после краша не проверены.
- Область: API worker, PostgreSQL, приватное S3-хранилище.

## Граница

Worker ведёт список ключей результатов, которые **сам успешно загрузил** в
текущем запуске job. Если загрузка следующего файла, запись метаданных,
проверка результата или финальный переход статуса завершаются ошибкой,
worker удаляет эти S3-объекты. После успешного удаления объекта удаляется
соответствующая строка `calculation_artifacts` по `job_id` и `object_key`.
Ключи проверяются на префикс `users/<job-id>/`; ключи чужих jobs и входных
datasets не участвуют. Успешные результаты не затрагиваются.

Условный переход в `succeeded` проверяется по числу затронутых строк. Если
владелец отменил job до финального перехода, worker не сообщает ложный
успех, очищает частичные результаты и не создаёт `failure.log`. Для
настоящей ошибки worker сначала фиксирует `failed`, затем публикует только
диагностический `failure.log`. Если запись его метаданных сорвалась,
загруженный объект журнала удаляется по возможности.

Очистка best-effort: если S3 не удалил объект, его metadata остаётся для
последующей сверки. Если S3 удалил объект, но БД недоступна, metadata может
временно указывать на отсутствующий файл. При краше worker список ключей
теряется. Следующий срез должен добавить сверяющий сборщик orphan, аудит и
политику retention; этот срез не является полным решением A6.

## Проверка

- Unit: только ключи текущего job; S3 удаляется раньше записи БД; ошибка
  одного удаления не останавливает остальные и не стирает его metadata.
- Интеграция: успешные четыре сценария сохраняют артефакты; обычная ошибка
  оставляет только `failure.log`, отмена — без опубликованных результатов.
