## Проблема и границы

Первый вертикальный срез кабинета выводил создание расчёта, загрузку входной
линии, историю и детали результата одним длинным экраном `/account`. Действие
работает, но пользователь не может перейти по прямой ссылке к расчёту и быстро
вернуться к активной работе без прокрутки между несвязанными блоками.

Этот срез вводит account shell, маршруты обзора, истории и детали job. Создание
job открывается модальным окном из обзора или истории, поэтому не занимает
отдельный пункт навигации. Он не меняет научные сценарии, DTO, API, S3, worker,
SQL или модель прав. Поиск, пагинация, повтор расчёта, проекты, каталог
наборов, удаление и точная воспроизводимость остаются отдельными следующими
срезами. Отмена существующего job получает понятное подтверждение, но её
серверное поведение не меняется.

## Контракты и данные

Экран использует текущие `CalculationJobDto`, `CalculationKindDto`, `DatasetDto`
и `@litora/api-client`. Создание job по-прежнему выполняет только `POST
/calculations`; список — `GET /calculations`, детали для полного, краткого и
сравнительного просмотра — `GET /calculations/:id`, отмена — `POST
/calculations/:id/cancel`. Обзор не обещает полноту истории: API возвращает
последние 100 собственных jobs без пагинации.

Новые URL браузера не передают UUID другого пользователя, S3-ключи, signed URL,
токены или параметры научного CLI. Владение остаётся проверкой API/SQL; 404
чужого или отсутствующего job не заменяется web-проверкой. Подписанная ссылка
запрашивается в деталях и не сохраняется в URL или browser storage.

## Риски и альтернативы

- Вложенные маршруты могут случайно создать второй navbar/footer. Account shell
  используется родительским маршрутом, а дочерние страницы рендерятся через
  `Outlet` без повторного layout.
- Модальный запуск и просмотр могут добавить водопад запросов. Для запуска
  kinds и datasets загружаются параллельно, сравнение запрашивает две детали
  параллельно; history и detail сохраняют раздельный polling с cleanup таймера.
- Подтверждение отмены и краткий просмотр используют native `<dialog>` в
  целевой Chromium-среде E2E. Окно нового расчёта использует shadcn/ui Dialog
  на Radix; его модальность проверяется отдельно в спецификации 0019.
- Список всё ещё ограничен текущим API. Нельзя маскировать это клиентской
  фильтрацией или писать «все расчёты»; server pagination — отдельный контракт.
