# 0013 — контроль временных результатов worker

- Статус: локальный срез A5; staging и жёсткая дисковая квота не подтверждены.
- Область: отдельный API worker и его каталог результата.

## Проблема и граница

Ранее worker проверял 100 МиБ/256 файлов только после завершения Go, перед
загрузкой в S3. Во время расчёта процесс мог создать больше данных на
временном диске. Теперь worker примерно раз в секунду обходит приватный
`output` текущего job, суммирует размеры регулярных файлов и считает файлы
и вложенные каталоги. Пределы: 100 МиБ, 256 файлов, 256 каталогов.
Символические ссылки и специальные файлы в результате недопустимы.

При превышении лимита или ошибке чтения каталога worker останавливает группу
дочернего Go-процесса и помечает job как `failed` с диагностическим журналом.
Перед публикацией результат проверяется повторно. HTTP-controller не запускает
Go и не содержит мониторинга. Отмена и timeout продолжают работать через
существующий механизм worker; условный переход статуса не заменяет
`cancelled` на `failed` или `succeeded`.

Это **программный периодический предел**, не жёсткая квота: быстрый всплеск
между двумя проверками возможен; место для входных данных, журналов и иных
временных файлов им не ограничено. До открытия `mesh`/`seabed` нужны
измерения пиков CPU/RAM/диска, лимит на весь рабочий каталог и жёсткое
ограничение контейнера/файловой системы. Redis или новая очередь этим срезом
не вводятся.

## Проверка

- Unit-тест: обычный вложенный результат принимается; превышение размера,
  числа файлов и символическая ссылка отвергаются.
- Интеграционный тест существующих четырёх HTTP-kind должен проходить без
  ложных срабатываний. Для доказательства жёсткого лимита нужен отдельный
  ресурсный smoke на стенде; этот срез его не заявляет.
