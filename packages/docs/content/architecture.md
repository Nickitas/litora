# Архитектура платформы Litora

## Роли приложений

Litora разделена на вычислительную плоскость и плоскость управления. `lito-cli`
владеет математикой, `lito-api` управляет пользователями и заданиями, а `lito-web`
предоставляет интерфейс.

```text
Browser -> lito-web -> lito-api -> PostgreSQL
                         |              |
                         |              +-> задания и метаданные
                         |
                         +-> S3/MinIO <- Node worker -> Go CLI / доменные пакеты
```

HTTP-запрос не ждёт тяжёлый расчёт. API создаёт задание и сразу возвращает его
идентификатор. Web наблюдает за статусом через polling; позднее при необходимости
можно добавить Server-Sent Events.

## PostgreSQL

PostgreSQL хранит пользователей, refresh-сессии, задания, статусы, параметры,
метрики, реестр файлов и аудит. Содержимое крупных SVG, JSON, MSH, VTU и CSV в БД
не хранится.

## S3

Результаты расчётов могут занимать сотни мегабайт. S3 предоставляет объектное
хранение, потоковую загрузку, контрольные суммы и временные ссылки. Локально тот же
протокол реализует MinIO. В PostgreSQL хранятся bucket, object key, MIME type,
размер и SHA-256.

## Docker

Docker Compose поднимает PostgreSQL и MinIO, а с профилем `app` — также API,
отдельный Node worker, запускающий Go CLI, и web через nginx. Для hot reload
приложения можно запускать на хосте. Подробности и актуальный план:
[Единая платформа](platform-integration.md).

## Почему пока без Redis

На первом этапе задания можно надёжно забирать из PostgreSQL транзакцией с
`FOR UPDATE SKIP LOCKED`. Redis и отдельная очередь понадобятся при измеренной
нагрузке, требующей сложных retry, приоритетов или большого числа worker'ов.

## Первоначальные этапы внедрения

Это исходная дорожная карта, не список оставшихся задач. Текущий статус и следующие
шаги — в [плане интеграции](platform-integration.md). Отдельный Go worker пока в плане;
сейчас отдельный Node-процесс запускает CLI.

1. Локальная инфраструктура: PostgreSQL, MinIO, environment configuration.
2. Пользователи и авторизация в API.
3. Модель задания расчёта и CRUD/status API.
4. Машинно-читаемый контракт входа/выхода Go-ядра.
5. Отдельный Go worker и запуск первого расчёта.
6. Загрузка артефактов в MinIO/S3 и signed URL.
7. Экран создания расчёта и просмотра прогресса в web.
8. Наблюдаемость, retry, отмена, лимиты и production deployment.

## Текущая модель хранения

PostgreSQL инициализируется идемпотентным SQL из
`infra/postgres/init/001_schema.sql`. Используются таблицы:

- `users` и `auth_sessions` — пользователи и отзывные access/refresh-сессии;
- `calculation_jobs` — параметры, состояние и итоговая сводка расчёта;
- `calculation_artifacts` — метаданные объектов в S3;
- `calculation_events` — журнал переходов и прогресса.

Worker сохраняет объекты с ключом `users/{jobId}/{relativePath}`, импортёр —
`calculations/{jobId}/{relativePath}`. API возвращает
не постоянный публичный URL, а подписанную ссылку с ограниченным временем жизни.

Для импорта уже созданного каталога CLI используется:

```bash
pnpm --filter litora-api artifacts:import -- ../lito-cli/output/platform-smoke smoke
```

Импортёр вычисляет SHA-256, загружает каждый файл в MinIO/S3 и записывает его
метаданные в PostgreSQL. Старые импортированные задания без владельца не выдаются
через пользовательский API; используйте запуск в кабинете для новых расчётов.
