# Артефакты вычислительного ядра

## Проверенный smoke-набор

Команды запускались на локальном сегменте Сочи с минимальными параметрами в
`apps/lito-cli/output/platform-smoke/`.

| Возможность | Результат | Файлы и форматы |
|---|---:|---|
| `source` | успешно | 2 GeoJSON |
| `map black-sea` | успешно | GeoJSON, SVG |
| `dimension` | успешно | JSON, 2 SVG |
| `mesh` | успешно | 3 GEO, 3 MSH, 3 SVG, 3 LOG, JSON, TSV |
| Исторический демо-запуск `erosion` | успешно в прежней версии | 2 JSON, 3 SVG |
| Исторический демо-запуск `all` | успешно в прежней версии | 3 JSON, 5 SVG |

Демо-строки фиксируют прежние артефакты, а не доступные команды: демо-флаги
и автоматическая подготовка удалены. Новые `erosion`/`all` требуют явных входов.
Тесты всех Go-пакетов проходят. Подкоманды `seabed` требуют производного набора
GEBCO с валидным паспортом, результатов `mesh` и последовательного выполнения
ADAPT-этапов. `calibrate-cerc` дополнительно требует реальные наблюдения. Эти
научные входы не генерируются искусственно при smoke-проверке.

## Виды научных рисунков

Вид результата определяется командой и паспортом, а не номером рисунка
или именем скопированного SVG. Все представления строит Go на выбранных
научных входах.

| Вид | Команда | Артефакт относительно `--output` |
| --- | --- | --- |
| Наблюдаемый берег и сетка box-counting | `dimension` с явным GeoJSON | `svg/dimension_0.svg` |
| Аудит масштабов и регрессии того же анализа | тот же `dimension` | `svg/dimension_loglog_0.svg`, `metrics/dimension.metrics.json` |
| Обзор глубин и изобат | `seabed render` с принятой моделью дна и паспортами | `seabed/svg/bathymetry-overview.svg` |
| Фактическая сетка: сложный берег, шельф, склон | тот же `seabed render` | `seabed/svg/mesh-details.svg` |
| Поле требуемого размера h(x,y), новая сетка ещё не построена | `seabed adapt` | `seabed/svg/size-field.svg`, `seabed/adaptive/size-field.csv`, `seabed/adaptive/size-field.json` |
| Анонимные карточки сравнения фактических сеток | `seabed compare-adaptive --expert-set` либо `seabed expert-set` по принятому ADAPT-03 и его файлам | `seabed/expert-set/cards/E-*.svg` и связанные материалы AI-01 |

`dimension` создаёт оба SVG в одном запуске. Исходные координаты и
масштабы берут из метрик; аналитическая сетка не является расчётной MSH.
Обзор глубин и фрагменты фактической сетки также создаются вместе.
Цвет глубины, размер h и качество формы ячейки показывают разные величины.

В новой форме выберите «Отчёты по модели дна» → «Подтип отчёта»: обзор глубин,
поле размера или фрагменты фактической сетки. Выбор сохраняется в задании;
после завершения выбранный SVG показан отдельно, дополнительные отчёты и
паспорта доступны рядом. Переключение подтипа сохраняет совместимые входы
и введённые параметры. Для API необязательный `input.reportType` принимает
`bathymetry_overview`/`mesh_details` у `seabed_render` и `size_field` у
`seabed_adapt`. Это выбор основного представления, не новый флаг CLI.
Задания без этого параметра сохраняют прежнюю галерею.

Для `dimension`, `dimension_dataset` и `dimension_file` основной отчёт
выбирается в поле «Вид отчёта box-counting». `input.reportType` принимает
`coastline_box_counting` (берег с аналитической сеткой) или
`box_counting_regression` (график регрессии). Файлы и метрики формирует Go;
подтип не меняет исходную геометрию и не добавляет CLI-флаг.

Публикационная компоновка `seabed figure-five` из трёх карточек AI-01
имеет иной смысл и окна, чем `mesh-details.svg`. Анонимный E-номер зависит
от состава набора и seed; алгоритм и диапазон размеров восстанавливают
по связанному ключу организатора, а не по номеру карточки. Закрытый ключ
не передают участникам слепой оценки. Для повтора нужны исходные MSH,
контур, поле размера, паспорта, контрольные суммы и версии вычислений.
Пресет параметров не доказывает тождества архивному рисунку.

Методики: [box-counting](fractal-analysis-scope.md),
[чтение модели дна](seabed-scientific-guide.md),
[сравнение генераторов](adaptive-generator-comparison.md) и
[экспертные карточки](expert-fragment-set.md).

## Правила сохранения

Один запуск CLI соответствует одной записи `calculation_jobs`. Каждый файл
становится записью `calculation_artifacts`, а его содержимое загружается в S3 с
ключом:

```text
calculations/{jobId}/{relativePath}
```

Для артефакта сохраняются исходное имя, категория, MIME type, размер, SHA-256,
bucket и object key. JSON-метрики дополнительно будут разбираться worker'ом и
записываться в `calculation_jobs.result_summary`, чтобы web мог показывать сводку
без скачивания больших файлов.

## Следующий контракт Go-ядра

Для надёжной интеграции каждая команда должна поддерживать машинный режим и
записывать единый `manifest.json`:

```json
{
  "schemaVersion": "litora-calculation-result/v1",
  "kind": "dimension",
  "status": "succeeded",
  "coreVersion": "2.0.0",
  "summary": {},
  "artifacts": []
}
```

Worker должен опираться на этот манифест, а не анализировать человекочитаемый
stdout или угадывать назначение файла по расширению.
